# Asuna development and interaction rules

Start with [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md): the repository map, where state lives, tests, and how to write a persona or channel package. The rules below are binding.

- `start-asuna.cmd` (Windows) or `start-asuna.sh` (Linux, macOS) launches the installed native DSH Web profile; `start-asuna-ui.cmd` is an alias and `asuna ui` selects the same profile. Interaction with her goes through that Web UI; there is no terminal chat.
- An agent that talks to a persona through any shared interface (her Web chat, a channel such as QQ, a peer bridge) says who it is when it starts and whenever it could be mistaken: which agent it is and that it is not the owner. It never writes as the owner or lets a message pass for the owner's.
- A coding agent talks to her on its own agent line, not in the owner's Web chat (there its words are recorded as the owner's). Each agent has one route of the `agent` channel and its own key, written by the Host at start to `<data>/private/route-keys/agent-<route>.json`: `python tools/agent_line.py send <route> "<text>"` posts, `python tools/agent_line.py poll <route> --wait 300` collects and confirms her answers, `status <route>` checks the line. Routes: `claude-code` for Claude Code, `codex` for Codex; another agent asks the owner for a route instead of borrowing one. She can close a line; while it is closed, posts are refused and her answers wait. See [packages/channels/agent-line/README.md](packages/channels/agent-line/README.md).
- Her self-development publications commit themselves in the checkout under her own git name (`character_git`). Nothing she publishes waits on an agent: an agent does not commit her files for her and does not hold her work up; it merges its own branches around her commits.
- Asuna runs on the owner's modified DSH: the fork https://github.com/eamars/deepseek-harness (branches `asuna/<version>`), pinned in `tools/dsh-inline/source.json`. Agents build on the pinned DSH as it is; upgrading DSH and keeping Asuna compatible with it is the owner's work.
- UI of our own design, or a replacement for DSH's shipped UI, needs the user's explicit approval before it is built; fixes and reuse of DSH's own UI facilities do not.
- UI development and review happen on an isolated native DSH profile, never her live one. Do not enable or call real model endpoints, including background summaries, unless the user explicitly authorizes resuming real-model use. The operator's external model server is independent of Asuna and must remain available for their own testing.
- Delivery tests must not tune Xiaoman's persona or wording to pass a test. Her runtime environment belongs to internal diagnostics, not QQ conversation; do not inject deployment details into her prompts to make an environment answer more accurate.
- Tests and probes must drop their owned Mongo test databases after exporting file evidence, including failure teardown. Do not retain databases for audit. Protect runtime and unrelated databases; skip Mongo tests when the service is unavailable.
- Whoever creates a workspace or data file under `<data>/` (a worktree, a probe or staging folder, a scratch data root, a dump) removes it when its job ends: a worktree when its branch is merged, a probe's folder when its evidence is exported. Only what current code or the live Host reads stays. Evidence kept past that is named in its ADR with its path and size, and is evidence only (manifests, small reports), never a working copy of data. The character's own files are hers.
- The current references are `README.md`, `README_CN.md`, `INSTALL.md`, `RUN_ASUNA.md`, `NATIVE_PLUGIN.md`, `RUNTIME_API.md`, `docs/DEVELOPMENT.md`, `docs/MODELS.md` and the package and tool READMEs. `docs/development_plans/**` keeps decisions and plans and is not authority for current behavior. A change to an interface updates its entry there.
- Current references show only the present state: what it is, how to use it, what it needs. No history, dates, ADR provenance or reasons; those belong in the ADRs.
- The core is persona-agnostic. Persona names, persona text, and persona-specific parameters live only in persona packages, persona-private data, or test fixtures; core code, core prompts, core tools, and example configs must not contain them.
- Personal data stays local. Real account IDs, addresses, host names, user names, time zones, and private content belong in ignored local config, MongoDB, or private source roots, never in tracked files. Examples use documentation-reserved placeholders. A deployment's private files live in `<data>/private/` (the worker's data root, `.runtime/` in a checkout): never committed, carried with the deployment's data, not with the code. Words that point at real people and places go in its list `personal-words.txt` (`category|word|why`; `ASUNA_PRIVATE_WORDS` names another file), which the character keeps with her `private_words` tool; `personal-denylist.txt` there holds the literals the release scan (`tools/check_staged_secrets.py --personal`) looks for. `tests/test_personal_words.py` refuses a committed file that contains one; on a machine without the list it is skipped and says so, which means unchecked, not clean. Never print a listed word: name its category and line.
- Program-computed state and statistics reach a model only as interpreted text from versioned tables (coarse tiers, explicit wording even for neutral); a model writes state through categorical choices that the program maps to values. Times, counts and identifiers are formatted for reading. State that is not about one person (mood and similar) is global across conversations; state about a person stays with that person.
