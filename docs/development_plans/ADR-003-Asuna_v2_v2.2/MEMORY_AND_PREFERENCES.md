# 真实记录、对话总结与个人／群偏好

## 1. 基线已经有用，不重建记忆系统

当前 `MemoryService.chunk` 已经按单条消息分段，不再静默丢掉超过900字节的原文；`MemoryIndexer` 已经后台索引；`Retrieval.search` 已有向量filter和返回前范围复查；`commit_understanding` 已由Gemma产生一次真实关系更新。保留这些实现。当前不足是它们仍面向本机单一scene/worker，且没有自动话题总结与群偏好闭环。

“写过日志”“生成过总结”“已经向量索引”“这次确实召回”四件事分别确认，不通过增加模型自检来混成一个成功标志。

## 2. 最少的数据扩展

优先扩展现有集合；字段是宿主内部数据，不是每轮模型必须输出的格式。

| 现有对象 | 本轮需要的含义 |
|---|---|
| `identities` | 可信QQ账号和可变展示名；显式关联本机owner，不能按昵称自动关联 |
| `scenes` | 私聊/群的授权范围、成员、处理位置、当前小话题、摘要处理位置 |
| `messages` | 原始文本/segment、speaker、平台ID、reply链、实际发布状态、不能丢失的完整正文 |
| `episodes/tasks` | 一次认知处理了哪些输入；执行目标、来源、返回场景、真实任务状态 |
| `memory_units` | 原文块、独白、事实性总结、偏好观察；保留不同的epistemic_type和来源 |
| `state_heads/state_revisions` | 角色/关系当前理解、个人偏好与群规范的可版本化正文 |
| `sessions` | 双lane会话绑定与各自压缩状态，不是全局人物的唯一储存 |

新建一个简单`runtime_events`承载已接受通道事件、定时触发、执行结果和发布确认的队列状态。计划语义可以新建`plans`或复用现有明确的状态对象；不要混入普通聊天的reported_speech。schema迁移只增所需集合/索引，不reset数据库。

**用事件序列跟踪后置整理，别仅按生成时的message scene_seq。** 文本生成后可能很久才收到平台确认；发布确认需要产生新的记录/dirty标记，让总结能吸收这次真实公开行为。不能因为cursor已经越过那条待发消息而永久遗漏它，也不能在确认前把它当已说过。

## 3. 自动记录是宿主职责

授权内入站先持久化，再交认知。monologue生成完成立即保存；公开草稿和实际平台确认分别保存；工具结果留任务记录，不混成Gemma直接经历过的全部细节。

使用已有Mongo写入确认。故障时保留实际异常和未处理状态，不用 `except Exception: pass`，也不打印计划条数当成功条数。确实数据库不可用时不假称“已记住”；不需要每轮再发一个模型调用重新确认落盘。

新场景进入后，把它标为需要分块/索引。一个共享后台worker可顺序处理dirty场景，优先新输入，限制一次批次；重启从库中未处理项继续，不要求用户手工index。近期未索引记录可明确通过原文回读，不能叫作向量命中。

用户“不记录/忘掉”不能只删除一个摘要继续保留同义私密内容：先采用当前已支持的删除范围并如实说明限制；别自动把整份私聊转成所谓“只记我的感受”绕过不记录请求。不在V2.2另建复杂隐私法务平台，但配置和既有删除语义不能被成长任务覆盖。

## 4. Bonus 总结：读得懂且可还原来源

### 何时生成

默认在QQ收发、多人范围与基本记录成立后再接。若外部群/账号条件缺失或定时能力独立受阻，可按 [STAGE_RECOVERY.md](STAGE_RECOVERY.md) 在身份、来源、隔离及持久化可靠的本机/私聊场景先验收个人子项；多人和真实群偏好结论仍需补验。以一段完整交流、适当的消息批次或一段安静间隔为触发；用户直接问“刚才聊了什么”时可以按需生成。只启动有限处理，不为每条群消息增加一次摘要调用。

聊天摘要整理可以低优先级使用现有Qwen，或者已经就绪的适配角色总结路径；不增加第三个常驻模型。若Qwen正在长任务中，就先用近期原文，摘要排队。不把后台worker当作无限并行的模型资源。

### 提供什么材料

程序提供当前场景中按时序的原文窗口和已有主题概况，每段带简短的发言者/来源标签。输入窗口边界、可用来源ID由程序掌握。模型不复制长UUID、哈希或假的来源标识。

预期自然语言总结示例（只说明写法，不是测试标准答案）：

> 这段交流有两条线：A 在核对线缆位置，B 在聊相机。A 将先前“左柜”更正为“右柜”，小满尚未实地核验。B 更希望看到推导过程；A 只要求这次核对先给结论。相机的话题还没决定具体型号。

总结不能把角色自己的偏好写成用户偏好，也不能把“我愿意试试”写成“已完成”。当前V1压缩摘要已有这类归属错误，所以本轮要看真实原文，不只看是否生成了摘要。

### 怎样保存

模型生成正文后，程序附加窗口、来源、scope、生成模型/时间，保存成功再推进该次整理位置。处理失败保留原文和dirty状态；不阻断下一句聊天。无法确定某条偏好的主体，就仅保存带归属不明提示的总结，不强行更新人物状态。

可以使用小的标签/分段来供程序选择写入目标，或将个人/群整理分别作为低频单步任务；不要把摘要全文强制变成几十字段的JSON，也不要为一个多余字段重跑整轮聊天。元数据格式由代码管理。

## 5. 个人偏好与关系理解不是一张表的同义词

个人偏好表达“这个人明确说喜欢什么”；关系理解表达“我怎样看待和回应这个人”。两者可以关联，但不能由“我觉得他很冷淡”创建一条客观人物事实。

建议目标：

- `preference:<person_id>`，限定到来源场景或明确授权的共享范围；内容是有来源的偏好及适用条件。
- `relationship:<person_id>`，沿用当前Gemma的关系正文修订。
- `group_preference:<scene_id>`，本群的明确约定和暂定的互动倾向。

若为减少改动将偏好暂存`memory_units`并在当前关系正文中引用也可，但必须能区分主体与范围。确需新增entity前缀时，由Codex明确扩展可写白名单，不放开任意状态字段。

个人偏好优先用直接陈述和更正；多次相同回忆不加“证据次数”。转述“他说他喜欢”仍是转述，不假装本人确认。不要自动抽取不相关敏感画像。

例：A说“对我先给结论，过程等我问”，B说“我喜欢听每一步”，必须分别作用；小满说“我喜欢逻辑谜题”不能归到A或B。身份可靠但记忆不共享时，不为了“认出了同一个人”就注入全部私聊。

## 6. 群偏好不是某个人替全群下令

区分三类：

1. **授权规则**：允许哪个群、谁能开发/操作哪些资源——只有host配置/owner授权决定，永不从群氛围总结产生。
2. **明确群约定**：有可确认的群管理约定或成员明确一致意见，例如“任务答案先短后长”。适用范围只到这个群。
3. **观察到的倾向**：大家经常简短开玩笑等，只能写成可修正倾向，不能宣称全体赞同。

一个人说“我们都喜欢长文”并不证明全群如此。普通成员可表达自己的偏好；若他具有实际群管理角色，可以提出群交流规则，但不能因此取得owner私聊或宿主权限。平台角色与Asuna管理权限不是同一个级别。

遇到个人与群习惯冲突，Gemma做情境取舍；必要时询问，不靠固定好感分覆盖。群偏好改变后下轮注入短快照，不重写整条persona前缀。私域来源不能自动升成global-safe的群规范。

## 7. 总结、记忆与compaction分工

原始消息是可查证的历史；长期总结是可修改的理解索引；native compaction是本轮工作上下文的容量管理。三个不同生命周期。

角色compact后，核心人格和当前适用关系/偏好来自已确认版本；摘要中的人物归属如果与原文/明确偏好冲突，以可核对来源校正，并保留误差记录。不要仅用“上一版摘要的摘要”滚动形成永久人物画像。

Qwen保存执行进度，不向Gemma复制完整操作记录。任务编号/权限/发送状态来自程序，不依赖任何模型摘要。后台总结服务访问范围也必须按scene限制，不能为方便把所有私聊放进一个跨scope长上下文。

## 8. 用户可见的证据

用户只需看一段总结和适用人物偏好，必要时通过operator trace查看来源。不在群里自动展示私人独白或整份档案。验收见B1/B2：新对话→自动保存→整理→离开短期尾部→恢复→实际使用；失败时显示停在哪一层。

元数据中的生成时间/来源由程序记录，不让模型宣称自己“已经全部记住”。原始完整保存与摘要事实正确性仍是两个不同结论。
