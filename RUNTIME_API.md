# Asuna Runtime API

This is the current business contract for the two native DSH plugins. See [NATIVE_PLUGIN.md](NATIVE_PLUGIN.md) for composition and [RUN_ASUNA.md](RUN_ASUNA.md) for installation. DSH owns model execution and Web sessions; its managed Python worker preserves the existing normalized channel API below.

## Runtime responsibilities

`RuntimeHost` inside the business worker owns Application, the queue/action `Chat` controller, memory indexing and summaries, and configured channels/integrations. The Core Host plugin owns actual native agents and the DSH schedule service. Native composer input enters through SessionController and is associated with persisted input by native message ID; the Web UI never reads a parallel Asuna chat store.

Inbound work is persisted before retrieval or model calls. Character turns and action tasks use separate queues. The host binds each turn and task to a scene, person, policy epoch, and capability set. A new context changes the DSH conversation context while retaining persisted scene memory.

A character turn is one native DSH turn. She first writes a short thought with `think` (she is asked for at most 300 characters and refused past 360, `role_tools.THOUGHT_HARD_CHARS`; it is kept as a monologue memory and her last few thoughts in the scene reach her next turn). She then uses the tools the program exposes for that turn: `recall`; her own records (`write_document`, `update_self`, `understand_person`, `set_policy`, `pin_memory`, `feel`, `promote_memory`); `plan`; `attach_image`; `group_action`; and `delegate`, `message_action` and `stop_action` to work with the action brain. A refused call is a tool error she reads and can correct in the same turn; it never fails the turn. `feel` without `op` but with a `kind` records; `plan` without `op` or `plan_id` but with an intent and a timing creates. Action tool arguments pass `tool_args.normalize` first: an `argv` written as a string holding a list is read as the list, `overwrite: "true"` as true, and a `development_database_read` limit over 50, a history `window_days` over 90 or an `integration_test` timeout over 60 is clamped to that bound; each change is listed in the result's `adjusted`. `development_database_read` also takes `sort` ({field: 1|-1}); an unknown collection's refusal lists the real ones; `development_write` on an existing file without `overwrite` refuses as `DEVELOPMENT_FILE_EXISTS`. Each call is keyed by its native call id, so a replay after a crash returns the recorded result. Her last text without a tool call is what she says; `stay_silent` ends a turn without speaking. The action brain uses the DSH loop and the tools granted to its task. `RETURNED` means the action turn returned; it does not establish that the requested goal was completed. The action brain returns a natural-language report; the program attaches the actual tool receipts. Delegation requires a workspace grant for the scene (the owner's local scene, or a channel route that names a workspace). The action brain's system prompt is `executor.md` plus the persona: with persona model `render.action_persona: values` (core default) only public sections tagged `render.values_tag`; with `persona` the persona document's every-turn sections readable in the class of the conversation the task came from. It never receives memory, relationships, emotion or other state.

Where the program needs a model's answer before it can go on (the end of a character turn, the relevance gate, an appraisal, the action brain's report, a dialogue summary), the answer is checked deterministically: it stopped on its own, it has text (thinking alone is not an answer; tool calls count only for the action brain), and it has that point's shape. The end of a character turn needs a `think` first and final text that is neither a JSON object nor talk about tools or program blocks; the gate needs 接话／不理 on its first line; an appraisal needs a JSON array. A failed check goes back to the model in the same session as a program note that names the problem, the way DSH returns a failed tool call (for her turn, in the same native turn), and the point asks again. After two repairs it fails with the named problem: her turn fails its episode, the gate lets the message pass quietly, an appraisal is skipped, an action ends `BLOCKED`, and a summary waits for its next run. Transport errors and empty completions are retried by DSH's own retry first, and an interrupted turn is not repaired. Each failed check is audited (`phase.rejected`, `execution.rejected`, `summary.rejected`).

Ordinary tool errors are returned to the active DSH action loop so it can inspect the error and continue. A task revision, cancellation, changed policy epoch, or expired lease fences further calls. The host records tool inputs and results as artifacts; result claims are checked against those records and any required effect receipts.

The active action lane uses DSH's native agent loop. Asuna does not add a fixed action-step termination limit or reject turns using a separate token-budget gate. Token measurements are observational; context pressure is handled through DSH compaction, using the selected native model metadata.

## Configuration

- `config/local.json` is the initial migration source. The example is `config/local.example.json`. After migration the DSH profile's Core `deployment`, `channelAdmission` and route settings are authoritative, and every secret is in DSH's credential store. Everything the profile writes goes to its data folder (the floor's `dataRoot`, default `$DSH_HOME/asuna/<profile>/`; the local chat works in `<data>/work/local-user`); locks that guard a database or an endpoint are per user (`ASUNA_LOCK_ROOT`, default `<temp>/asuna-locks`), so two profiles on one database still exclude each other.
- Model credentials and initial route defaults may be supplied in an adjacent `*.models.local.json` file; after installation active routes are saved in the native profile. The character and action routes are independent; either may use the same or a different configured provider and model.
- An adjacent `asuna-channel.local.json` is loaded only when `enabled` is `true`. Its example is `config/asuna-channel.example.json`.
- An adjacent `integration.local.json` provides the optional owner-bound managed integration profile. Its example is `config/integration.example.json`.
- Credentials, account IDs, scene IDs, provider addresses, and local paths come from deployment configuration. They are not fixed by lane name or stored in this contract.

Core's native plugin settings page uses DSH's settings mirror, staged form controls, revision fence and durable profile writes. A business secret is a reference in the settings, `{"$secret":"ASUNA_MONGO_URI"}`, named like an environment variable; its value lives only in DSH's credential store, which also holds the LLM provider keys. Any key whose name contains `mongo_uri`, `api_key`/`apikey`, `token`, `password` or `secret` must be such a reference. Core resolves the references when the worker starts or a proposal is validated and hands the values to the worker for that run; the settings page writes keys straight into the store and shows only whether each is configured. Save performs model-free validation. Apply quiesces ingress and background summaries at an idle user/action boundary, restarts the worker, and reloads an already-enabled adapter from the installed channel package. A settings startup failure restores the previous runtime configuration while retaining the saved proposal for correction.

Native `asuna/stage` informational events attribute each actual request's `turn`, `step`, `operation`, `lane` and `phase`. Stage input notices also retain `source.lane`; `asuna/stage-result` links the final original assistant sequence to the same attribution. These envelopes are ignorable by plain DSH readers and contain no duplicate assistant content. Client projection uses DSH's location store and original assistant events, including native stream settlement and older-page loading. Brain names describe responsibilities, independently of provider/model. Only her turn's final text, accepted by the end-of-turn check and stored as `SPEAK` rows, is an outward expression; neither a successful model call nor a stored row is a platform delivery receipt. The worker ends each character turn with a `turn_done` event once it needs no further stage (a repair note continues the same turn).

Host restart marks unfinished managed actions/results `PAUSED` with `pause_reason=host_restart` and advances their fencing token; it does not enqueue action execution or old result feedback. Native execution bindings, artifacts and results remain intact. A new explicit request in the existing local conversation may continue it with `message_action`, which reuses the prior execution binding under a new task grant. Internal opportunities and stale feedback cannot resume paused work. Pending feedback checks its original durable input's task/revision before and after model stages and at effect boundaries. Cancellation, revision or restart pause suppresses further stages; completed public history is retained. An in-flight output may remain in diagnostics, but it cannot become another decision or publication after suppression.

`delegate {title, brief}` creates a task whose action session starts with her brief, followed by the program's facts (the original message, the workspace, attachments, grants). `message_action` on her own READY or RUNNING task records her words (`task_messages`) and injects them into the running action session at its next step; words that a run ended before reading start one more round in the same session. On a finished task it creates a continuation task on the same execution binding; a cancelled, paused (except by a new local request) or differently granted task refuses it in words. `stop_action` cancels a READY or RUNNING task and fences its execution. Her words never add a grant: a task keeps the grants of the turn that created it. Tool calls carry their immutable operation binding; a delayed old call cannot acquire the successor's grant from a mutable session record. Task context prioritizes live work and then durable input time, rather than the number of database writes, so recently returned work remains available for continuation.

Continued tasks on the same authorized execution binding reuse their actual native action session via `agents.create/resume`. Each task receives its current grant and system context; a different role, actor or policy epoch cannot import the old source. The plugin admits a successor after the preceding native Turn and handle teardown, without blocking its business result acknowledgement. Her conversation shows each task as one collaboration thread, recorded as `asuna/collab` events in her session: her brief and later messages, the action brain's questions, progress notes and reports, her answers, status changes, and the action brain's own work between them as ranges of its native session (never copies of its records). Entries carry ids, so a replay adds nothing; entries that arrive during one of her turns are appended once she is idle. Receipt replay does not execute a completed stage. The business-bound action preset uses foreground native handles; it does not accept generic human prompts through DSH's continuation manager, which inherits the role preset rather than the required action composition.

## Channel API

When channel routes are configured, the host binds the channel server to `127.0.0.1`; the default port is `8766`. It is separate from the Web UI and is not exposed through the Web proxy. Each configured channel has a unique bearer token of at least 24 characters. A route binds the platform account, sender, Asuna person, scene, and publication target.

A configured channel's id names its platform (`channels.qq`), and that platform's channel package must be installed. A channel package (`packages/napcat-qq`) calls `registerChannel({kind, title, project, resource_root, python, module, integration_directory, skill_directories})`. Its Python kind module gives the platform's id formats (`qq:<account>`, `qq:<bot>:<dm|group>:<target>`), how the adapter writes a real @ in inbound text and how her @ reaches it, the media hosts vision may fetch from by default, and the adapter's derived settings. Its adapter is the integration that her owner-granted `integration_*` tools develop and run, from the package's own development project. Its skill joins her skill directories. A platform's conversations live in a workspace named by its title.

`channelAdmission=automatic` admits authenticated, valid platform messages from previously unknown DMs/groups/members. The adapter derives `auto-dm-<id>` / `auto-group-<id>` route IDs; existing configured targets keep their routes. Core persists admissions in the existing `artifacts` collection and creates separate per-member channel workspaces without owner grants. An automatically admitted group member does not start another conversation or bump the group's authorization epoch. Removals/blocking revoke membership; old task epochs remain fenced. `explicit` requires configured enrollment. Both modes honor channel `blocked_senders` and `blocked_groups` before admission and outbox delivery.

Receipt projects to the target's real native QQ conversation before inference, including non-waking group activity. It uses the original durable input ID to deduplicate; an acknowledgment in `sink_receipts` permits projection retry after interruption without replaying execution. Historical rows predating projection migration remain in Memory. DSH requires a conversation's first visible entry to be the system head her agent writes on its first step, so until she has had a turn in a conversation its lines wait in that conversation's DSH inbox (next-step, the newest 40; older ones stay in Memory). Her first step there claims them right after the head, in arrival order and before the stage notice, which leaves out of its history what they already show. A line that arrives while that first turn is starting waits for its head. DSH lists a conversation in the sidebar from its first turn. The Web composer is view-only for QQ; native archive hides until the next platform activity.

All endpoints require:

```http
Authorization: Bearer <channel-token>
```

POST bodies are JSON objects, limited to 256 KiB. Unsupported envelope fields are rejected.

### Receive an event

```http
POST /v1/channels/{channel_id}/events
Content-Type: application/json
```

Direct message example:

```json
{
  "route_id": "authorized-dm",
  "account_id": "configured-account",
  "sender_id": "configured-sender",
  "event_id": "platform-event-id",
  "text": "Message text",
  "occurred_at": "2026-01-01T00:00:00Z"
}
```

`route_id`, `account_id`, `sender_id`, `event_id`, and `text` are required. `occurred_at` and `raw` are optional. Text is limited to 16,000 characters. The host derives person, scene, and target from the route; callers cannot supply a scope, task, or internal episode kind. Of `raw`, the host stores only the sender profile in `raw.asuna_peer` after checking it against the authenticated sender and group, the media block in `raw.asuna_media`, and `raw.group_name`; the platform event itself is not stored. Every QQ person, configured or automatically admitted, is `qq:<account>`.

Group events use the same endpoint and add `group_id`, `mentioned_account_ids`, and optionally `reply_to`. These values must come from the adapter's parsed platform event. Direct-message routes reject group-only fields. The host checks the configured group and member bindings. A group event wakes the character only under the configured mention and saved-reply rules; other authorized group messages can be persisted without starting a character turn.

Quoting (owner 2026-10-06; people in her groups quote about 16% of lines, she quoted 92%): in a group her first message of a turn quotes the line that called her only when someone else has spoken since that line; her other messages never quote. Her `quote` tool (`how`: `source` | `none`, group turns that answer a line) overrides this for the turn, e.g. `none` for a bot command that must go out bare. Direct chats quote the line they answer as before (`publish._quote`).

A group message wakes her for one of these reasons. An @ of her account or a reply to a message of hers runs her full turn. The others go through the relevance gate first:

- a reply inside a thread she was in;
- her name without an @ (her display name or the persona's `people.self_names`);
- the proactive rules of a group that opted in;
- a chain (below);
- an awaited answer: her newest delivered line in the group was addressed to someone — the people she @-tagged by label and the author of the line she answered (`channels.addressees`), waited on by default like a reply (owner 2026-10-06) — and within `channels.AWAIT_SECONDS` (180 s; in her groups 90% of human answers come within about 3 minutes) one of them writes a line that @s and quotes no one. `await_answer` (`wait`: `no` turns it off for the turn; `yes` with `why` waits for anyone when the line is addressed to nobody). One look per line of hers (`wake_reason: awaited_answer`); her turn carries `awaited_from_program`.
- someone on her watchlist (owner 2026-10-06, `watches.py`): the `watch` tool (`op` `on` with `person` — a label, `#number`, name or id that names exactly one person in the conversation she is in — `hours` 1–72, `mode` `once` (default: the first time they speak, then done) or `burst` (again after 10 quiet minutes, until it expires) and an optional `why`; `op` `off` with the `id`) keeps at most 5 people in `watches`, one per person. A line from a watched person in any of her conversations sets `event.watched`; in a group whose line has no other wake reason it is `wake_reason: watched`, one look through the gate. In a private chat the line is already her turn. Her turn carries `watched_from_program`, and every turn `watching_from_program` (who, roughly how long is left, the mode, and the why only in a turn of the class she wrote it in). An expired watch is not a turn: the next turn's block carries one `ran_out` line on how often they appeared, once. The tool is offered in groups and private chats, and anywhere while the list is not empty. Nothing a watched person says is copied to another conversation.

The gate is one short request in a small per-group child session (`asuna-attend-…`, preset `asuna-attend`). It runs on the character route at a low effort, and compacts at about 5% of the context window. It reads only words:
- why she is asked;
- the speaker's label, notes and familiarity;
- the lines since she last spoke there (at least 10, at most 60 minutes back, at most 40 lines);
- how long ago that was;
- her public mood.

She answers 接话 or 不理 with a short reason. An answer in another shape is told so and asked again; after two repairs, or when the gate cannot answer at all, the message passes quietly. 不理 commits the episode before any recall (`processing_outcome: ATTEND_QUIET`). 接话 prepares her full context, says her reason in `attend_from_program`, and continues (`ATTEND_JOIN`). Every other message is stored without a turn.

In a group, a turn's history covers the same catch-up window, and never fewer than the last 12 lines. Every line says when it was said on her clock face: a platform line entering her conversation ends its label line with the local month/day and time (`[名字 #4] 10/5 08:19`), and a history row carries `at` in the same form instead of raw timestamps. A group turn also carries `pace_from_program` (versioned word tables in `places.py`, nothing advisory): when the last line was, when the current stretch of talk began (a pause of 30 minutes or more ends a stretch) and how much it holds, and the pause before it with how much has been said since the line before that pause. Whether an older line is still the topic is hers to judge. `deployment.reasoning_effort` sets the character route's effort per stage, where the model offers it: `attend` (default `low`) for the gate, and `group` for group turns. The local chat keeps the route's own effort.

The host persists accepted input before any retrieval or model call and returns:

```json
{"status":"accepted","episode_id":"ep-…","received_at":"…"}
```

An identical event for the same channel, account, route scene, and platform event ID returns `duplicate` without a second queue entry. On a peer line she has closed herself (a direct-message route of a channel kind that declares `PEER_LINE`, ADR-013 §6), the host returns `{"status":"line_closed"}` and keeps nothing: the message is passed over, not queued for later. Reusing an event ID with conflicting identity or content is rejected. `accepted` confirms durable host receipt, not a reply or publication.

Adapters that normalize media may provide bounded metadata under `raw.asuna_media`. The host does not interpret arbitrary platform payloads. Media metadata and an image placeholder do not mean the character brain has seen the image; image reading is described below.

### Claim public output

```http
GET /v1/channels/{channel_id}/outbox?wait_seconds=25&supports=image
```

`wait_seconds` is capped at 25. The host atomically claims a queued public `SPEAK` message and returns its frozen target, text, publication ID, attempt ID, and optional platform reply target. Internal monologue, reasoning, traces, and tool output are never placed in the outbox.

`supports` is an optional comma-separated list of what the adapter can handle today (`supports=image,sticker`). An adapter that does not declare a capability receives text only. When a message carries an accepted image and the adapter declared `image`, the item also carries `attachment` metadata — `{artifact_id, media_type, sha256, size}`, never base64; the bytes come from the endpoint below. When the adapter did not declare it, the text still goes out and the message row records that the picture did not (`attachment_skipped`), so delivered history cannot later claim an image arrived that never left the host. A message that is one sticker (ADR-016) is offered only to an adapter that declared `sticker`: its item carries `text: ""` and `sticker` — `{"kind": "custom"}` with the picture as `attachment` (send it as a picture marked as a sticker), or `{"kind": "market", "emoji_id", "emoji_package_id", "key", "summary"}` (send the store sticker by its ids, no bytes). Without `sticker` declared the row is failed with `CHANNEL_DOES_NOT_DECLARE_STICKER`. Her words may carry `[表情:名字]`, a platform face by name, for the adapter to turn into the real face.

The adapter sends only the returned text — plus the declared attachment, when the item carries one — to the returned target. Starting an adapter or claiming a message is not a platform receipt.

One reply may leave as several messages. When the persona model sets `speak.max_messages` above 1, a platform turn's context carries `speak_from_program`, a note telling her that her words go out as one message unless she writes the marker (`speak.split_marker`, default `[分条]`) where one should end. The core breaks the reply there, never inside a fenced code block and never on blank lines; pieces past the limit join the last message, and the local chat gets no note. Each piece is its own outbox item with `not_before` set by typing pace (`speak.chars_per_second`, clamped to `speak.min_gap_s`…`speak.max_gap_s`), and a piece is claimable only after the one before it settled: a failed or unknown piece cancels the rest (`CANCELLED_AFTER_FAILURE`). A picture rides on the first piece.

What she says is every text she writes in the turn, in order — text written beside a tool call included, since her conversation shows each as hers; with more than one, each is its own message where the persona allows several, else they join as paragraphs. A received line joins her conversation as it arrives, so a running turn sees lines that arrive between its steps. A line belongs to the first turn that had it in view (it reached that turn's model request): when that turn ends with speech or a deliberate silence, every such line still queued for its own turn is marked `absorbed_by` that episode and completes as `SEEN_IN_TURN` without a model call, so one line is never answered twice. A line that arrives after the turn's last request is not in view and gets its own turn. Platform turns are told both rules (`speak_from_program`).

### Fetch attachment bytes

```http
GET /v1/channels/{channel_id}/outbox/{publication_id}/attachment?attempt_id=…&artifact_id=…
Authorization: Bearer <channel token>
```

The same channel token authorizes this request. It returns the bytes of the one artifact that this publication's own claim declared, with `Content-Type` taken from the file signature. Only a publication currently in `SENDING` whose `attempt_id` matches the request may read it. The artifact must belong to that message's own scope, and the stored bytes are re-verified against the row's `sha256` before anything is written to the socket. `artifact_id` is optional and only ever narrows the request: a different artifact is refused, never substituted.

A row that records `attachment_skipped` is treated as never having declared the picture: its metadata stays on the row so delivered history can say the message was meant to carry one, and the byte endpoint refuses it with `ATTACHMENT_NOT_DECLARED` rather than handing out bytes for an image that never went out. A later claim that does carry the image clears that marker, so the flag always describes the current attempt.

Refusals are `403` with a code — `PUBLICATION_NOT_FOUND`, `PUBLICATION_ATTEMPT_MISMATCH`, `ATTACHMENT_NOT_DECLARED`, `ATTACHMENT_ARTIFACT_DENIED`, `ATTACHMENT_SCOPE_DENIED`, `ATTACHMENT_SHA_MISMATCH`, `ATTACHMENT_HASH_MISMATCH`, `ATTACHMENT_NOT_AN_IMAGE`, `ATTACHMENT_OVER_LIMIT`, `ATTACHMENT_MEDIA_TYPE_MISMATCH` — and carry no partial body. The adapter re-checks the digest and the file signature on its side. Neither side treats a successful claim as proof the image arrived: only a platform receipt says that.

### Record a platform receipt

```http
POST /v1/channels/{channel_id}/outbox/{publication_id}/receipt
Content-Type: application/json
```

```json
{
  "attempt_id": "claimed-attempt-id",
  "status": "platform_accepted",
  "platform_message_id": "platform-message-id",
  "response": {"platform": "response"}
}
```

`status` is `platform_accepted`, `failed`, or `unknown`; `response` must be an object. `platform_accepted` requires a non-empty `platform_message_id` and records `DELIVERED` with `delivery_basis=platform_ack`. It means the platform accepted the message, not that a person read it. A matching receipt may be repeated idempotently; a conflicting attempt or terminal receipt is rejected.

If the send result cannot be determined, the adapter records `unknown`. A host restart converts an in-flight `SENDING` attempt to `UNKNOWN`. The host does not automatically claim it again. A later definitive receipt for that same attempt may resolve the state.

### HTTP outcomes

- `400` — malformed JSON, invalid size, or invalid field values.
- `403` — authentication, route, identity, capability, or receipt denied.
- `404` — unknown channel endpoint.
- `503` — host-side service failure; the host records a redacted diagnostic.

## Action capabilities

Action tool visibility is bound to the persisted task grant and route configuration. The action lane receives the DSH-native `skill`, `todo_write`, `web_search`, and `web_fetch` capabilities, plus Asuna tools allowed for that task.

Commands the worker does not write itself run under DSH's own sandbox (owner 2026-10-06): the Host wraps each one with `ctx.sandbox.confine` (dsh-sandbox-local — a restricted token on Windows, bubblewrap or Landlock on Linux, Seatbelt on macOS) in `workspace-write` mode, so it may write only its own folder: a task's folder for `sandbox_run`, the candidate for `development_run`, the output folder for a persona job, the data folder for an integration run. Reads and the network are not restricted. Which sessions may run commands at all is decided by the tools a task is given: `sandbox_run` is offered only to tasks from the owner's own scenes (her local chat and the owner's DM), and elsewhere her capability list says the action brain cannot run code there. Commands are native to the machine: `python3` is the worker's Python, and an argument `/task` names the task folder. `list_files`, `read_file` and `write_file` are done by the worker itself inside the task folder, protected sources read-only. The Host says at initialize whether it can confine; `deployment.sandbox.backend` is `auto` (default) or `none`. Without a Host sandbox, or with `none`, `sandbox_run`, the managed integration process, persona jobs and self-development are off: the tools are not offered, her capability list says these cannot be handed over, and the settings card's status line names the backend (`dsh`) or the reason there is none. On Windows the Host must be able to change permissions on the data folder (DSH grants each confined folder to the command and leaves that grant standing).

Asuna tools include scoped workspace operations, history search, structured discussion digest, `ask_character`, `report_progress`, and `read_image` when the action route declares image input. `read_image` is shared by both brains: her turn offers it when her own route declares image input and the conversation's recent pictures include one that can be pulled, or when her turn has pictures it may send (`image_artifacts_from_program`). Besides a message attachment ref, `read_image` takes the `artifact_id` of a stored image: one in the task's or turn's own scope, one she made herself (source `integration:`, from any scene), or one this turn was offered to send. Any other id answers `IMAGE_ARTIFACT_NOT_READABLE`, the same as an unknown one. This is how a picture is looked at again after it was drawn or before it is sent. Owner grants can add managed integration tools or self-development tools. A tool being registered does not grant it to every task. `import_integration_artifact` belongs to the managed integration group, not to the ordinary workspace group: a QQ task's grant never carries it. `generate_image` is granted to every task, from any conversation, whenever the integration is enabled and its profile has an endpoint named `image` (below).

`ask_character` asks her for a judgment that is hers and waits: her role session runs an internal turn (`think`, optionally `recall`, then `answer_action`) whose answer returns as the tool result. It creates no public reply, task or authority. `report_progress` leaves her a note without waiting; she reads it on her next turn.

## History, retrieval, and summaries

Conversation and memory records are scoped by scene and policy epoch. Memory indexing runs in the background. History search reads authorized inbound messages and delivered `SPEAK` messages; it can return literal matches and, when available, semantic candidates. It does not turn a derived summary into a verbatim quote.

Structured discussion digests use the same scene-bound history reader. They report their actual time and source coverage, preserve source references, and identify partial results rather than claiming an unread window was fully covered.

Background dialogue summaries process new messages in direct-message and authorized-group scenes after the summary boundary is initialized. They include inbound messages and delivered public `SPEAK` messages, and do not block the conversation. Each summary stores its source IDs, source window, participants, and per-speaker attribution. The participant list is computed from stored authors, not inferred by the summarizing model. Correction annotations resolve only against records in the same scene and policy epoch; unresolved references remain unresolved. When a later correction points to an earlier summary, the host appends a correction marker without rewriting the earlier summary text. A summary is evidence for a person only when its recorded participants include that person.

## What a turn carries

The program adds most of a turn's context by itself, so it also bounds it (`context_budget.py`, versioned; ADR-014). Nothing is cut silently: what a turn leaves out is counted and said, and stays readable through `recall`.

- **Per block.** Her mood lists every unsettled feeling and the strongest others up to 6, with `fainter` counting the rest; times are coarse words and event ids are 12-character prefixes (`feel` close/void accepts a prefix that names one event), so an unchanged mood reads the same from turn to turn. How to record a feeling is its own block, `how_to_record_from_program`. The clock is `clock_from_program`; how to write a plan, `schedule_control_from_program`, no longer changes with it. Her ideas list open ideas before deferred ones (at most 20) and says how many more wait.
- **Her notes.** A note shown every turn (`inject: always` sections of a group's notes or a ledger, corrected sections left out) has a per-turn limit: 2,400 characters for a group's notes, 4,000 for each ledger. Within it the note shows whole, with `fullness` in words. Over it, the newest sections that fit show whole and the rest are named in `not_shown` by heading. A note more than twice its limit takes no new text (`NOTE_OVER_LIMIT`, said in words) until she shortens it, merges sections or tucks some away; shrinking edits always pass. Her understanding of a person, her character core and her current self are written whole and take at most 4,000 characters each. The persona and voice render has a fixed budget of 16,384 UTF-8 bytes by default (`render.budget_tokens`, which she may set up to 32,768).
- **Public words reach home only through her own review (ADR-017, owner 2026-10-06).** The recent experience a home heartbeat or self-improvement turn carries lists every line of her private conversations (`visibility.owner_private_scenes`) but only her own delivered lines from groups, other people's private chats and peer lines; a task from such a conversation keeps its headline, not its report. How the groups are going reaches home as words (`places_from_program`). Other people's words come home only through her ideas notebook (decided in self-improvement turns, with a reason) or a nightly `promote_memory`, which requires `why`, keeps it on the memory and audits `memory.promoted`. Every other home turn carries `elsewhere_from_program` (`places.elsewhere`): per other conversation in the last 6 hours (groups, others' chats, and her other home lines marked （家里）), what she herself did there in words (how much she said, how many of her pictures and stickers she sent, the tasks she handed over and their state), never anyone's words; without it a home turn took her own pictures for someone else's (owner 2026-10-06). Home conversations are her local chat, the owner's direct chats, and conversations of a channel kind that declares `HOME = True` (`dsh-peer`: the owner's own agents); QQ and any other platform kind are outside. In a home turn someone wrote (`external`: the owner, or a peer on a home line; not her heartbeat, plans or nightly turns, which have `visit`) she may be sent on an errand: the turn carries `errand_places_from_program` (her unblocked groups and configured direct chats outside home, by name) and the `errand` tool (`place`, `request` ≤ 500 characters, optional `exactly`). It queues a `visit` input there with intent `errand` (`visit:errand:<scene>:<event>:<call>`, so two errands in one turn are two), up to 20 a day, outside the visit limits; the visit records who asked (`author`, and `by` when it was not the owner) and `errand.offered` audits it. That turn is public, sees only that chat and `visit_from_program.request`, named as whose words they are (`exactly` asks her to relay them prefixed 「<who>让我转告」, 主人 for the owner), and may stay silent. An errand may carry one of her own pictures (`artifact_id`; that turn's `image_artifacts_from_program` always lists it, as a visit's does). Pictures are offered only where the channel kind carries them (`TEXT_ONLY = True` on `dsh-peer`); a group or anyone's DM other than the owner's gets only pictures she made (`outbound_media.own_only`). A `share_picture` visit does not wait for a quiet room; `start_topic` does. Integration (LAN device) tools are granted to the owner in the local chat and in their own platform DM (`integration.owner_dm`, by route and canonical person). From a home turn her `plan` create may name a peer line (`line`, as listed in `lines_from_program`): the plan is stored, fires and is changed in that line (`from_scene_id` records where she made it), and home turns list it under that line as `your_plans_there`. Home turns then carry `errands_from_program`: where she went, what was asked, and a program state word — never what anyone there replied.
- **Nightly tidying.** Her settlement turn carries `notes_review_from_program` when notes are due: over or near their limit, or changed and not tidied for 7 days, at most 3 a night, most pressing first, each with its sections. Tidying is hers (rewrite, merge, tuck away, or leave as is); the program never edits or deletes her text.
- **The whole turn.** Past 48,000 JSON characters the oldest rows of a few lists go first — recent experience, promotion candidates, recalled memories, the topic thread, then history down to its last 4 lines — and `trimmed_from_program` says what was left out. The worker records the turn's size as `context_chars` in its manifest and audits each trim as `context.trimmed`.

## People in conversations

Identity is the account: an author's `person_id`, mapped to its canonical person by `canonical_persons`. That mapping is read from configuration only, so removing an alias immediately ends owner-private access for that entry point. A display name never decides who someone is. Each person gets a fixed label in each scene the first time they appear (`[name #n]`, stored in `scene_people`). The number never changes, so renames, members who share a name, and compaction neither merge nor split people. Names come from the verified platform profile on that person's own messages; a name the operator set in `identities.display_name` takes precedence for everyone except the owner. Names are NFKC-normalized, reduced to one line of visible characters, and stripped of the characters labels are built from (`[ ] 【 】 「 」 『 』 # < >`).

In the character's conversation, a QQ message is its label line followed by the message text indented by two spaces. A reply adds an indented `> 回复 <label>：<excerpt>` line. An @mention of a known person reads as that person's label, and a mention of her own account reads as her name. After the label, the program notes in words: a group owner or admin role, another member with the same or a look-alike name, a name containing the owner's label or her own name, and a rename within the last 24 hours. The owner's label starts with the persona's `people.owner_label` (core default `本机用户`) and is decided by account. Context blocks name authors by `speaker` label instead of author ids, and a recalled summary gives `who`, `about_current_speaker` and correction sentences. The summarizing model receives the same labels. QQ numbers stay in program data. Her context names conversations instead of giving their ids: `scene` is 本机私聊, 群聊「name」 or 私聊 with the person's label, and a row or memory from another conversation carries that conversation's name (a shared memory reads 不分场合, an owner-only one 只在私下). Scene ids, scope keys, policy epochs and platform message numbers are not in her context.

To @ someone in a group she writes their label (`@[name #4]`, or `@#4`). The outbox turns it into the adapter's `@qq:<account>` marker when the item leaves the host; the stored message keeps the label, and a label that names nobody in the scene is sent as a plain `@name`. A stored `@qq:<account>` reads back to her as the label.

The history and discussion-digest tools take `person` as a label, a `#number`, an id, or a name. A name resolves against the scene's people (current, former and operator-given names, and names shown on their own verified messages); when it matches several people the tool answers with their labels and runs no query, and the filter is always by author, never by a name on a message. Results name writers by label and carry no author or person ids.

How well she knows the current speaker reaches her in `relationship` as words: `familiarity` is one level (the owner; known, when she has written an understanding of them or answered them many times; regular; met; new), computed from the owner's account, her written understanding, the turns in which she answered them and the lines they wrote, across every conversation of the canonical person. Nothing a message says raises it. A persona words each level and gives its `stance` in `people.familiarity`. `understanding` is what she has written about them. No relationship record is seeded: everyone starts with none, which reads as 你还没写过对这个人的理解, and her first reflected understanding creates the record.

## Her place in a group

Her own role in each group reaches her in words in `your_place_from_program`: 群主, 管理员, 普通成员, or not yet known. The adapter asks the platform for the logged-in account's own role (cached for ten minutes) and sends it in `raw.asuna_self`. The host keeps only a valid role, and only on group events.

Where she is the group's owner or an admin, the block also tells her how to use her `group_action` tool:

- `kind`: `mute`, `unmute`, `recall` or `kick`;
- `who`: a label or `#n`;
- `duration`: 1分钟, 10分钟, 1小时 or 1天 (mute only);
- `which`: 这条 or 他刚才那条 (recall only);
- `reason`.

The program refuses any of these, by name:

- she is not an admin;
- the route sets `admin_actions: false` (admin actions are on by default);
- the target is unclear or unknown;
- the target is the owner, herself, the group's owner or another admin;
- a mute without a duration;
- there is no recent message to recall (recall takes the message that woke her, or the target's last line within 10 minutes);
- more than 6 actions in an hour in that group.

An accepted action becomes a `group_action` artifact. The outbox hands it to the adapter before any message, and the adapter calls `set_group_ban`, `delete_msg` or `set_group_kick`. The platform's answer arrives through the same receipt endpoint and updates the artifact (DONE, FAILED or UNKNOWN). An action interrupted while it was being sent becomes UNKNOWN and is never retried. Her words for the result say 已交给平台，等确认 until the platform answers; the account and message numbers stay in program data.

`group_notes_from_program` shows her own notes about the group: who is who, its customs, how she acts there. She writes them from that group's own turns with `write_document` and `doc: "group_notes"` (`append_section`, `replace_section`, or `set_tags` to tuck a section away with `inject: "on_demand"`). The program maps that name to the group's document and keeps its sections public to that group, also when she tidies them from home by the document name her nightly settlement lists. The block shows the notes within their per-turn limit (see What a turn carries).

## Media and image reading

An adapter may normalize non-text segments into bounded `raw.asuna_media` metadata. The host preserves placeholders and does not treat them as visual input. The action task receives a bounded list of image attachments from its own scene and policy epoch, plus images from scenes it may read only through a configured cross-scene read link; every entry carries `scene_id` and `linked_scene`, so the listing states where each image came from.

The action brain can call `read_image({"ref": "…", "max_bytes": 4194304})` when `executor.input_modalities` includes `image`. The reference selects an attachment already visible to that task; it cannot widen the read scope. That scope is recomputed from configuration at call time (`context_links` or route-level `read_scenes`, own scene first), so deleting the configured edge returns to own-scene-only, and a linked scene missing from the database or sitting in another policy epoch is simply not scanned. Bytes pulled from a linked scene are still stored under the calling task's own scope key. URL fetching requires an allowed host and safe redirect, enforces a byte limit, and accepts PNG, JPEG, WebP, or GIF data identified by file signature. An optional local image directory can also be configured. Pulled bytes are stored through the scoped blob store and passed to DSH as a durable image attachment. The stored tool receipt contains metadata and blob references, not base64 image bytes.

The character brain has the same tool (ADR-011 §5.3 as amended, owner 2026-10-05). Her turn offers `read_image` when `character.input_modalities` includes `image` and the conversation's recent pictures — the same window, fences and linked scenes the action brain reads — include one that can be pulled. The call runs in her turn's scene and scope, stores bytes the same way, and becomes an image attachment in her turn; the episode's `tool_calls` and the audit keep only the receipt. A platform line entering her conversation names its pullable pictures under the text (`（图 ref：att-…）`), and her media note tells her to look herself, or to put the `ref` in the brief when she hands picture work to the action brain. Looking does not wait on sending: in an owner-private turn where none of her pictures can be sent (her local chat has no channel route), her newest own pictures — at most 5, ids and when — are listed as `your_pictures_from_program`, and `read_image` comes with them. A picture the model refuses does not end the turn: DSH stores a looked-at picture in the conversation's session log and rebuilds every request from it, so when the provider refuses a request from one of Asuna's sessions as invalid (`INVALID_REQUEST`, e.g. a WebP its server cannot decode) while the conversation still sends pictures, the plugin records one DSH `image/offload` decision for every retained picture there — they become DSH's "image omitted" placeholders from then on — and the request is tried once more (`image-refusal.js`). A refusal with no picture left to omit ends the turn as before.

The default byte limit equals the 8 MiB hard limit: QQ photos are routinely 4-6 MiB and DSH re-encodes request images toward a 1 MiB target, so blocking at pull time would be an Asuna fence, not a route capability. Host allowlists, timeout, local directories, and insecure HTTP policy are configured under `vision`; the allowlist defaults to the multimedia host this deployment has actually received. Unsupported routes, disallowed sources, and fetch failures return real error codes, and a non-2xx response carries the server's bounded reason with any temporary `rkey` redacted; placeholders are not reported as viewed images. Download URLs are re-read from the stored message at pull time and are never embedded in the listing or truncated. Durable image references enter the native attachment pipeline; request image limits and pricing belong to the selected DSH provider. There is no Asuna token proxy.

A picture the owner attaches in her local chat stays in her conversation, so a character route that declares image input sees it directly; past the route's image budget, DSH's image offload — mounted once by its base profile for every session; a second mount in a preset breaks session resume — swaps the oldest for placeholders and retries. The plugin also reads each attached picture back from DSH's attachment store (at most 8 per input) and passes it with the input; the host stores it as an image artifact in the local chat's scope (source `local-upload:<input id>`, once per input) and records it on the input row as `raw.asuna_media` with `origin: local_upload`, its placeholder leading the text — so history and recall keep it after compaction, a picture-only message is a valid input, and a picture that could not be read is recorded as such. Her turn's media note says the picture is already in the conversation; the action brain reads it by `ref` from the blob store (`pulled_via: blob`, no host allowlist, nothing stored twice). Only the program's own local input can name such an artifact: a platform message carrying the same fields is not pullable from the blob store. As her image in the local chat it can be attached in the owner's linked QQ DM, never in a group.

### Sending an image with her words

A turn may also carry an image out. When the scene is the owner's own private conversation (`session_class=owner_private`) and its channel route targets a `dm`, the context gains `image_artifacts_from_program`: the image artifacts this turn may reference, each with `artifact_id`, `sha256` and `size`, plus a note that these are program-held artifacts and not file paths. Only then does her turn offer the `attach_image` tool (`artifact_id`, `why`): one picture per turn — calling it again replaces the first — and only an `artifact_id` from that list. A direction this version does not open, an artifact that was not offered this turn, bytes that are not an image by file signature, or a size over 8 MiB is refused as a tool error with its code and reason, and she can still finish the turn. A turn that ends with `stay_silent` sends no picture. In a group she is in (a group scene with a group route), the list holds only pictures she produced herself — bytes from her own generator (`generate_image` or `import_integration_artifact`, source `integration:`), from whichever of her scenes they were made in — never a picture someone sent her; she decides whether and where to send one, always all-ages (owner, 2026-10-05). The tool and the attachment endpoint refuse anything else in a group with `ATTACHMENT_NOT_HER_OWN`. Other people's private conversations, and a private scene routed to a group, are refused deterministically instead of silently degrading into text whose receipt reports a picture as delivered.

Her credentials (owner 2026-10-07, `credentials.py`): a credential is a name, a note and up to 6 environment variables. Values live in DSH's credential store, one record `asuna-cognition-core/<name>` (kind `grant`, payload `{note, env}`), read and written by the Host on the worker's `credentials` request. At home (owner-private `external` and `task_feedback` turns) the character brain's `credential` tool files one (`keep` with `name`, `note`, `env`; again under the same name to replace it) or removes it (`drop`); the value passes her model in that call only. Home turns and home tasks list `credentials_from_program` / `facts.credentials`: names, notes and variable names, never a value. Only a task from home may use one: `sandbox_run` with `credentials` (names) sets those variables for that one command (`CREDENTIALS_HOME_ONLY` otherwise). Every stored value, as written or URL-encoded, is replaced by `[凭据已隐藏]` in tool results and receipts, in her briefs and messages to the action brain and in its reports. A script that holds a value could still send it out over the network; the protection is that no model holds it. The core skill `asuna-credentials` teaches the rules, including using someone's account only for what it was granted for.

Stickers and the platform's own faces (ADR-016, owner 2026-10-06). A sticker is a picture someone sent *as a sticker* — still or animated, or a store sticker — never a photo; the adapter marks it on the media item (`sticker: custom|market`), and for items stored before it did, the platform's channel kind tells from the item (`sticker_of`). A platform line names its stickers under the text as `（表情包 ref：att-…）` and its other pictures as `（图 ref：…）`. In a conversation whose platform sends stickers (`channel_kinds.sends_stickers`), her turn carries `stickers_from_program` — her shelf by name, each with her note on when it fits, how often she has used it in words, the shelf's count and fullness word — and `faces_from_program` — the face names people there used lately — and offers the `sticker` tool: `keep` (a sticker `att-` ref from this conversation, or the `blob-` id of a picture she produced; a `name` of up to 12 characters and a `when` of up to 40), `drop` and `rename`. A photo is refused (`STICKER_IS_A_PHOTO`), so are a name or sticker she already keeps, and a full shelf (`STICKER_SHELF_FULL`, 60, `context_budget.STICKER_SHELF`). Keeping a custom sticker pulls its bytes once into `global-safe` (source `sticker:<message>`); a store sticker keeps the platform ids it is sent again by. To send one she writes `[表情包:名字]` in her speech: it leaves as a message of its own, one per turn, its row keeping the token as text and carrying `sticker` (and, for a custom one, the picture as `attachment`, which the attachment endpoint serves to any conversation that takes stickers because it is on her shelf). `[表情:名字]` inside her words is a platform face; the adapter turns a known name into the real face. Her speech is sent back in the same turn when it names a sticker she does not keep, more than one sticker, a face name the platform does not know, or either where stickers cannot go (her local chat). At home `stickers_from_program` lists the shelf for tidying, and the nightly settlement carries `stickers_review_from_program` once a week (or whenever the shelf is 80% full): the stickers kept two weeks and never sent, or not sent for two weeks, at most 6. Rotating is hers — the program never drops one. The candidate pool (owner 2026-10-06): every sticker posted in a group is saved as it arrives (`stickers.pool_seen`, off the input path; bytes in `global-safe`, source `sticker-pool:<message>`) into `sticker_pool`, merged by picture or store id with how often and where it was seen, skipping what is on her shelf; past `POOL_MAX` (30) the least recently seen leave. Her nightly settlement carries `sticker_candidates_from_program` (the 8 most posted) and a group turn the ones posted there in the last 2 hours (4); each `candidate` is an artifact id she may `read_image`. `sticker` `keep` with `candidate` puts one on her shelf only if she looked at it in that turn (`STICKER_CANDIDATE_NOT_LOOKED`), under her name and note; it then leaves the pool. Stickers she knows (owner 2026-10-06): `sticker_memory` keeps, per persona and for good, what she called a sticker, keyed by a fingerprint — a store sticker's `market:<emoji_id>`, or `md5:<hex>` of a picture's bytes, which the channel kind can read from a media item without fetching it (`channel_kinds.sticker_md5`; QQ names the file by it). Every sticker she keeps is known by its name and note (rename updates it; dropping it does not forget it; at startup `remember_shelf` covers the shelf as it is), and `sticker` `remember` (an `att-` ref or a `candidate`, with `name` and `when`) records one she looked at in that turn and does not want to keep (`STICKER_NOT_LOOKED`, `STICKER_NO_FINGERPRINT`); remembering again replaces her words. When a known sticker is posted, its line reads `（表情包 ref：att-…，你认得：「名字」，她的说明；在你架子上|你收过又放下了|你看过没收）`, also when the picture itself can no longer be pulled. A known sticker is never a pool candidate, and a candidate she remembers leaves the pool. `read_image` of a sticker adds a `sticker_note` pointing at `remember` and `keep`. A claim that does not declare `supports=sticker` gets no sticker row: it is failed with `CHANNEL_DOES_NOT_DECLARE_STICKER` rather than sent half.

Two things put images on that list: bytes this scene already stored (`read_image`, and `import_integration_artifact` when the imported bytes turn out to be an image), and images registered in **one other scene belonging to the same person**. That exception exists because an import runs only in the local owner task (and a picture is often made there) while the turn that speaks the picture is usually the QQ private chat, and both entries are the owner's own private space. `outbound_media.image_scopes` computes the readable set from configuration at read time: this turn must be `owner_private`, the peer scene must be a `dm` whose canonical person is the same owner, and the two scenes must be joined by a `context_links` / route `read_scenes` edge. Between two owner-private scenes of one person the edge counts in either direction — neither end can downgrade owner-private data into a public session, which is what `visibility.without_link_downgrades` exists to refuse. Groups, another person's scenes, unlinked scenes and public turns never extend the list, and offered items that came from the peer scene say so (`from_linked_scene`, plus its `scene_id`). The attachment endpoint recomputes the same list from the publication row itself (scene, the person on its route, session class): a caller cannot pass a scope, and deleting the configured edge returns the fence to own-scene-only without any code change.

An accepted attachment writes metadata only, on the first `SPEAK` row (`attachment`); bytes stay in the scoped blob store and travel over the attachment endpoint above. Delivered history then shows the picture as something she sent, with its media type and size, and says so differently when the adapter never declared image support, when the platform receipt's attachment evidence does not match the stored digest, or when the row was never delivered. Text-only messages keep their previous shape exactly: no attachment slot, no extra wording, in her context and in history search results.

## Schedules

The host uses DSH's native scheduler; it does not run a second host timer wheel. Scheduling, updating, or cancelling a plan is a character decision in the authorized scene. A due plan re-enters that scene and asks the character to decide what to do. A due event is not new authorization and does not mean its requested work has completed. Plan status and policy epoch are checked before dispatch. In a platform conversation (a group or a DM) the due plan is a core notice, not a platform input: it carries no channel envelope, so it is never re-checked as a member's message or shown in that conversation's session as one; it wakes the conversation as a scene tick, the plan's person must still be a member of the route (`SCHEDULE_ROUTE_REVOKED` otherwise), and what she says goes out on the conversation's own route, with no platform message to reply to.

Asuna reuses an installed DSH Schedule service. When the Host has none, it mounts that same service once, unless the `asuna-cognition-core` setting `mountSchedule` is `false`; then plans, heartbeat and settlement are off. By DSH design the `schedule_*` tools of a mounted Schedule are visible to every root agent in the Host; Asuna's role and action presets restrict their own tools.

Her rhythms — the heartbeat (`presence`), nightly settlement and self-development — are plans the program owns: they never appear in her plan list, so her plan tool cannot cancel or retime them. The heartbeat runs at home, in the owner-private scene named by `persona_runtime.<persona>.heartbeat_target`, when her persona model also sets `heartbeat.enabled`; only the owner turns it on or off (a package may default `heartbeat.enabled`, never declare it as a policy key). Its pace is hers through core policy keys: `heartbeat.every_min` (15–240; anything outside is clamped), `heartbeat.min_gap_min` (0–720), `heartbeat.skip_in_sleep`, and `heartbeat.pause_min` (0–720: beats skip until then and resume by themselves; 0 resumes now). Before any model call a beat is skipped, with one counting audit, when a role turn is running or queued at home (the action brain working on a task does not count), during her pause, within `min_gap_min` of her last internal turn at home (heartbeat, settlement or self-development) unless something reached her since — an inbound message that woke her in any routed scene, or a finished task — in her sleep window when she chose `skip_in_sleep`, or after 24 beats that reached the model on that local day. A watchdog checks after every turn, at every settlement and self-development dispatch, and every five minutes from the host's existing watch thread: a heartbeat with no dispatch for two beats plus five minutes is audited as `rhythm.heartbeat_missed`, its native record replaced, and her next beat tells her it was reconnected. The five-minute check also recreates a native record deleted elsewhere and restores her pace on one retimed elsewhere (audited as `rhythm.retimed` with `drift`).

The owner sees her reminders in DSH's own task page (the Automation tasks entry; `@deepseek-ai/dsh-client-ui-schedule`, mounted by the core without the optional bundle's time context, which would show the browser's zone to her turns). Each task is named as she reads it — her plan's own words, or `心跳 · Heartbeat`, `夜间沉淀 · Nightly settlement`, `自我改进 · Self-improvement` — with its next run and delivery records; the scheduler session logs what DSH changes on a record (its next target after a delivery, an edit in that page) so the worker reads each record as it is now. `/heartbeat` in any session gives her one heartbeat now through the same path, skipping the gates (audited as `presence.forced`, and her beat says it was knocked early), and replies with the next scheduled beat; it creates no model message.

A heartbeat at home, or a plan of her own that comes due there, may send her on a visit (ADR-012). With `heartbeat.visits` on, her presence turn — and a `scheduled` turn in an owner-private conversation — carries `places_from_program`: each routed, unblocked group as words only — how busy it is and when the last line was, how many people spoke in the last hour, when she last spoke there, her last visit and what came of it, whether someone called her since she last spoke, her notes' headings, and whether she can go now — plus `last_visits_from_program`. No line anyone wrote crosses. The `visit` tool (`place`, `intent` = `start_topic` | `share_picture` | `check_in` | `write_notes`, optional `topic` ≤ 80 characters and `artifact_id` of a picture she produced) is offered only there, once per turn, and is refused with the reason when the group is not open to her now: today's `heartbeat.visits_per_day` (0–8, default 4) used up, night there (the route's P5 quiet hours, or 23:00–08:00 host time), within `heartbeat.after_own_min` (30–1440, default 360; doubled when what she last said there got no answer) of her last speech or visit there, or — for `start_topic` and `share_picture` only — someone spoke within `heartbeat.quiet_min` (0–240, default 30); going to look or take notes while people talk is fine. A visit whose input failed never got there: it comes home as such and spends neither her day nor the group's wait. An accepted visit queues an internal `visit` input in that group (`visit:<scene>:<beat event>`, wake reason `visit`). It carries no channel envelope — it is her own moment, not a platform message, so the group's session never shows a member saying it — and wakes as a scene tick; what she says goes out on the group's own route. the turn is `public` because the scene is, titled "Her own visit", and sees that group's catch-up, her group notes, her produced pictures and `visit_from_program` (why she came, her topic, the room in words, whether anyone called her) — no relationship, speaker, rhythm, cross-scene experience or home places. It has no `visit` tool and no development grant. What she says there counts toward P5's per-group caps.

A chain calls her in any of her groups (owner 2026-10-06), whether or not P5 is enabled there: when the newest line ends a run of the same text — or the same picture or sticker, by file, or store sticker, by id — from at least three different people, with no line of hers inside it, the line is woken with reason `chain` (`group_context.chain` = what, how many people, whether it is media). Only the night quiet hours (the route's `proactive` block even when it is off, else 23:00–08:00) and a busy foreground hold it; the burst, cooldown and hourly gates do not, because a chain is fast. One chain calls her once (`proactive.chain.woke` on the line); her own line ends the run. ## Managed integration and self-development

The managed integration runner is available only to the configured local owner profile. The adapter's code lives in its channel package and changes only through the development tools. `integration_test` runs a frozen, read-only `/app` copy of the development candidate's adapter with separate writable `/data`; `integration_start` enables a frozen copy of the published adapter as a managed process, and host restart restores the then-published adapter. Unpublished edits never run as the managed service. `integration_status` reports process state and bounded logs, not platform connectivity or delivery. `integration_stop` stops the managed process and disables host restart restoration.

Integration processes run under the Host sandbox like any command: they may write only their data folder, and reach the configured endpoints directly at each device's own address (the adapter settings may still name an endpoint by its configured local `port`; the run's settings carry the device's address instead). Their commands are argument arrays, not host-shell strings; `/app`, `/data` and `/integration/config.json` in an argument name the run's frozen adapter copy, its data folder and its settings (also `$ASUNA_INTEGRATION_CONFIG` and `$ASUNA_INTEGRATION_DATA`). Connection credentials come from the local integration profile and are not copied into ordinary task files. A test run (`integration_test`, unpublished adapter code) uses the real settings and can act on a platform for real (owner 2026-10-06: tools, not relays, are the boundary — the integration tools are owner-only); messages are meant to leave through the outbox and the published adapter started with `integration_start`. Each run's copy of the adapter is removed when it ends; only the service's copy is kept. An endpoint marked `"tls": true` is reached over TLS without verifying the device's certificate; `"read_only"` is a description of the device, not enforced.

`import_integration_artifact` reads one artifact over one of those configured endpoint aliases: the model supplies the alias and a path, never a URL, host or port, and the fetch performs a single HTTP/1.1 GET without following redirects. The host writes the bytes into the task workspace bound to this action at a relative path — existing files are kept unless `overwrite=true`, protected inputs are never written through, and the size cap is 4 MiB (1 MiB by default). The result reports the relative path, absolute path, byte count and SHA-256 actually written, or the real failure: unknown endpoint, URL rejected, path outside the workspace, target exists, over limit, HTTP status or transport error. When the bytes actually written are a PNG/JPEG/WebP/GIF by file signature (not by file name or `Content-Type`), the host additionally registers them as an `image` artifact in the scope this task is bound to — never a scope the model names: `kind=image`, `storage=gridfs`, `state=DONE`, media type from the bytes, and a SHA-256 the host recomputes and re-reads itself, with the result then carrying an `artifact` block (`artifact_id`, digest, size) so a later turn can send that picture out. Bytes that are not an image change nothing: the result keeps exactly its previous field set and no artifact row is written. A registration that cannot happen (a scope the store does not know, bytes over the 8 MiB outbound cap, a storage error) never turns a completed import into a failure — the reason is reported honestly under `artifact`. Offline: `python3 tools/integration_import_offline_check.py` and `python3 tools/outbound_image_offline_check.py`.

`generate_image` draws one picture with the endpoint aliased `image`, for any task (owner, 2026-10-06): the integration tools stay owner-only, and this tool is the one fixed sequence of that service's agent API (`project-comfyui-agent/v1`). The model supplies a prompt and a few choices — an optional ready text-to-image `workflow` id (otherwise `POST /project/resolve` picks one with `content_mode=sfw`, optionally for a `style`), `negative_prompt`, `width`/`height` (64–2048, multiples of 8), `seed`, and `options` limited to `steps`, `cfg`, `sampler_name` and `scheduler` that the workflow's `parameter_schema` declares — never a request, URL or path. The host runs `integration_image.py` as a trusted one-shot integration run that knows only the `image` endpoint and carries no adapter settings: it checks the workflow, `POST /project/generate` with `batch_size` 1, polls `GET /project/jobs/{prompt_id}` and fetches the first `/view` output (at most 8 MiB). The runner lock covers only the launch, so integration tools, status and stop do not wait behind a generation. A job still queued or running when `timeout` (default 180 s, at most 300) runs out is reported with its `prompt_id`; calling again with `job` collects it without drawing again. The host verifies the byte count and SHA-256, writes the picture into the task workspace (a new file under `images/`, or `target_relative_path`; never over an existing file) and registers it in the task's own scope with source `integration:image:<view path>`, so it counts as her own picture. The service's refusal (HTTP status and its `error` object) is returned as it was. `workflows=true` draws nothing: it lists the ready text-to-image workflows with the service's own guidance for each (prompt style and structure, quality prefix, best for and not for, recommended size, an example prompt), and every drawn result carries the same guidance for the workflow that drew it. Without a named `workflow` the service picks a generic anime one, and some workflows (such as Qwen-Image) are chosen only when named, so the brief says to list first. Nobody has seen a drawn picture until a model looks: the result and the brief say to call `read_image` with its `artifact_id`, compare it with what was asked and draw again when it is wrong. The task brief names this tool first for pictures; public generators reachable by `web_fetch` stay allowed, but their pictures cannot enter the workspace and can only be linked. Offline: `tests/test_image_generation.py`.

Self-development uses persistent project candidates separate from ordinary task workspaces. The default target is the selected persona package; `project="core"` selects the authorized cognition source. Tools inspect bounded file pages, edit/run candidate files, read bounded records from the existing database, and publish frozen artifacts after a non-consuming boot probe. Persona resources activate without restarting DSH. Python code replaces the worker at an idle boundary; JS/composition/dependency changes return `HOST_RESTART_REQUIRED`. Failed candidates remain for forward correction through the independent native recovery preset. The development tools come only with work the owner asked for in a private chat (local or the owner's DM) or that she handed over in her own self-improvement turn; any other scene's request can only become an entry in her idea notebook (`note_idea`), read and decided only in her self-improvement turns or a private chat with the owner (`read_ideas`, `review_idea`). The memory tab's owner-private view lists the notebook and her decisions.
