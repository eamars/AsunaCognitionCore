# Asuna Runtime API

The business contract between the worker, the Host plugin, channel adapters and the brains' tools. See [NATIVE_PLUGIN.md](NATIVE_PLUGIN.md) for composition and [RUN_ASUNA.md](RUN_ASUNA.md) for installation. DSH owns model execution and Web sessions; its managed Python worker serves the normalized channel API below.

## Runtime responsibilities

`RuntimeHost` inside the business worker owns Application, the queue/action `Chat` controller, memory indexing and summaries, and configured channels/integrations. The Core Host plugin owns actual native agents and the DSH schedule service. Native composer input enters through SessionController and is associated with persisted input by native message ID; the Web UI never reads a parallel Asuna chat store.

Inbound work is persisted before retrieval or model calls. Character turns and action tasks use separate queues. The host binds each turn and task to a scene, person, policy epoch, and capability set. A new context changes the DSH conversation context while retaining persisted scene memory.

A character turn is one native DSH turn. She first writes a short thought with `think` (she is asked for at most 300 characters and refused past 360, `role_tools.THOUGHT_HARD_CHARS`; it is kept as a monologue memory and her last few thoughts in the scene reach her next turn). She then uses the tools the program exposes for that turn: `recall`; her own records (`write_document`, `update_self`, `understand_person`, `set_policy`, `pin_memory`, `feel`, `promote_memory`); `plan`; `attach_image`; `group_action`; and `delegate`, `message_action` and `stop_action` to work with the action brain. A refused call is a tool error she reads and can correct in the same turn; it never fails the turn. `feel` without `op` but with a `kind` records; `plan` without `op` or `plan_id` but with an intent and a timing creates. Action tool arguments pass `tool_args.normalize` first: an `argv` written as a string holding a list is read as the list, `overwrite: "true"` as true, and a `development_database_read` limit over 50, a history `window_days` over 90 or an `integration_test` timeout over 60 is clamped to that bound; each change is listed in the result's `adjusted`. `development_database_read` also takes `sort` ({field: 1|-1}); an unknown collection's refusal lists the real ones; `development_write` on an existing file without `overwrite` refuses as `DEVELOPMENT_FILE_EXISTS`. Each call is keyed by its native call id, so a replay after a crash returns the recorded result. Every text she writes in the turn is what she says, in order, text beside a tool call included; a message without a tool call ends the turn, and `stay_silent` ends it with nothing more to say: words she already wrote in the turn still leave, and a turn with none sends nothing. Her instructions (`prompts/common.md`, `prompts/turn.md`) state the same contract. The action brain uses the DSH loop and the tools granted to its task. `RETURNED` means the action turn returned; it does not establish that the requested goal was completed. The action brain returns a natural-language report; the program attaches the actual tool receipts. Delegation requires a workspace grant for the scene (the owner's local scene, or a channel route that names a workspace). The action brain's system prompt is `executor.md` plus the persona: with persona model `render.action_persona: values` (core default) only public sections tagged `render.values_tag`; with `persona` the persona document's every-turn sections readable in the class of the conversation the task came from. It never receives memory, relationships, emotion or other state.

Where the program needs a model's answer before it can go on (the end of a character turn, the relevance gate, an appraisal, the action brain's report, a dialogue summary), the answer is checked deterministically: it stopped on its own, it has text (thinking alone is not an answer; tool calls count only for the action brain), and it has that point's shape. The end of a character turn needs a `think` first and final text that is neither a JSON object nor talk about tools or program blocks; the gate needs 接话／不理 on its first line; an appraisal needs a JSON array. A failed check goes back to the model in the same session as a program note that names the problem, the way DSH returns a failed tool call (for her turn, in the same native turn), and the point asks again. After two repairs it fails with the named problem: her turn fails its episode, the gate lets the message pass quietly, an appraisal is skipped, an action ends `BLOCKED`, and a summary waits for its next run. Transport errors and empty completions are retried by DSH's own retry first, and an interrupted turn is not repaired. Each failed check is audited (`phase.rejected`, `execution.rejected`, `summary.rejected`).

Ordinary tool errors are returned to the active DSH action loop so it can inspect the error and continue. A task revision, cancellation, changed policy epoch, or expired lease fences further calls. The host records tool inputs and results as artifacts; result claims are checked against those records and any required effect receipts.

The active action lane uses DSH's native agent loop. Asuna does not add a fixed action-step termination limit or reject turns using a separate token-budget gate. Token measurements are observational; context pressure is handled through DSH compaction, using the selected native model metadata.

## Configuration

- `config/local.json` is the initial migration source. The example is `config/local.example.json`. After migration the DSH profile's Core `deployment`, `channelAdmission` and route settings are authoritative, and every secret is in DSH's credential store. Everything the profile writes goes to its data folder (the floor's `dataRoot`, default `$DSH_HOME/asuna/<profile>/`; the local chat works in `<data>/work/local-user`); locks that guard a database or an endpoint are per user (`ASUNA_LOCK_ROOT`, default `<temp>/asuna-locks`), so two profiles on one database still exclude each other.
- Model credentials and initial route defaults may be supplied in an adjacent `*.models.local.json` file; after installation active routes are saved in the native profile. The character and action routes are independent; either may use the same or a different configured provider and model.
- An adjacent `asuna-channel.local.json` is loaded only when `enabled` is `true`. Its example is `config/asuna-channel.example.json`.
- An adjacent `integration.local.json` provides the optional owner-bound managed integration profile. Its example is `config/integration.example.json`.
- Credentials, account IDs, scene IDs, provider addresses, and local paths come from deployment configuration. They are not fixed by lane name or stored in this contract.

Core's native plugin settings page uses DSH's settings mirror, staged form controls, revision fence and durable profile writes. A business secret is a reference in the settings, `{"$secret":"ASUNA_MONGO_URI"}`, named like an environment variable; its value lives only in DSH's credential store, which also holds the LLM provider keys. Any key whose name contains `mongo_uri`, `api_key`/`apikey`, `token`, `password` or `secret` must be such a reference. Core resolves the references when the worker starts or a proposal is validated and hands the values to the worker for that run; the settings page writes keys straight into the store and shows only whether each is configured. Save performs model-free validation. Apply quiesces ingress and background summaries at an idle user/action boundary, restarts the worker, and reloads an already-enabled adapter from the installed channel package. A settings startup failure restores the previous runtime configuration while retaining the saved proposal for correction.

Native `asuna/stage` informational events attribute each actual request's `turn`, `step`, `operation`, `lane` and `phase`. Stage input notices also retain `source.lane`; `asuna/stage-result` links the final original assistant sequence to the same attribution. These envelopes are ignorable by plain DSH readers and contain no duplicate assistant content. Client projection uses DSH's location store and original assistant events, including native stream settlement and older-page loading. Brain names describe responsibilities, independently of provider/model. Only her turn's final text, accepted by the end-of-turn check and stored as `SPEAK` rows, is an outward expression; neither a successful model call nor a stored row is a platform delivery receipt. The worker ends each character turn with a `turn_done` event once it needs no further stage (a repair note continues the same turn).

Host restart marks unfinished managed actions `PAUSED` with `pause_reason=host_restart` and advances their fencing token; it does not enqueue action execution. A finished action whose result had not reached her is not paused: the handover watchdog hands it back. Native execution bindings, artifacts and results remain intact. A new explicit request in the existing local conversation may continue it with `message_action`, which reuses the prior execution binding under a new task grant. Internal opportunities and stale feedback cannot resume paused work. Pending feedback checks its original durable input's task/revision before and after model stages and at effect boundaries. The handover watchdog (`handover.py`) runs in the worker every minute, first one minute after start, and reads task state only. A finished task whose result is neither taken nor queued or being handed back is handed back again by its cause: a hand-back that failed before her turn gets the full result once more and then the short version (her brief, the report text cut at 3,000 characters with the cut stated, and when the run finished, without tool records); one whose turn on it failed gets the short version; one lost without an error (a restart) gets the full result. When the short version fails too, the task's `feedback_state` becomes `UNDELIVERABLE` and the program leaves the developer a note in `developer_inbox` (`source.by: program`). A `RUNNING` task whose lease expired while the worker is not running it is closed as `BLOCKED` (`failure_type: ORPHANED`) and handed back. Elapsed time is never a failure; `claim` records `started_at`. Her task list (`task_state_from_program`) gives each task one `status` phrase instead of its raw state fields; a task carried on by a later one (`continues_task_id`) points to that one. `elsewhere_from_program` uses the same phrases. Cancellation, revision or restart pause suppresses further stages; completed public history is retained. An in-flight output may remain in diagnostics, but it cannot become another decision or publication after suppression.

`delegate {title, brief}` creates a task whose action session starts with her brief, followed by the program's facts (the original message, the workspace, attachments, grants). `message_action` on her own READY or RUNNING task records her words (`task_messages`) and injects them into the running action session at its next step; words that a run ended before reading start one more round in the same session. On a finished task it creates a continuation task on the same execution binding; a cancelled, paused (except by a new local request) or differently granted task refuses it in words. `stop_action` cancels a READY or RUNNING task and fences its execution. Her words never add a grant: a task keeps the grants of the turn that created it. Tool calls carry their immutable operation binding; a delayed old call cannot acquire the successor's grant from a mutable session record. Task context prioritizes live work and then durable input time, rather than the number of database writes, so recently returned work remains available for continuation.

Continued tasks on the same authorized execution binding reuse their actual native action session via `agents.create/resume`. Each task receives its current grant and system context; a different role, actor or policy epoch cannot import the old source. The plugin admits a successor after the preceding native Turn and handle teardown, without blocking its business result acknowledgement. Her conversation shows each task as one collaboration thread, recorded as `asuna/collab` events in her session: her brief and later messages, the action brain's questions, progress notes and reports, her answers, status changes, where a finished run's result stands on its way back to her (handing, taken once her turn on it finishes, or missed: never handed back, her turn on it failed, or a Host restart came first; then handed back again, or final), and the action brain's own work between them as ranges of its native session (never copies of its records). Entries carry ids, so a replay adds nothing; entries that arrive during one of her turns are appended once she is idle. Receipt replay does not execute a completed stage. The business-bound action preset uses foreground native handles; it does not accept generic human prompts through DSH's continuation manager, which inherits the role preset rather than the required action composition.

## Channel API

When channel routes are configured, the host binds the channel server to `127.0.0.1`; the default port is `8766`. It is separate from the Web UI and is not exposed through the Web proxy. Each configured channel has a unique bearer token of at least 24 characters. A route binds the platform account, sender, Asuna person, scene, and publication target.

A configured channel's id names its platform (`channels.qq`), and that platform's channel package must be installed. A channel package (`packages/channels/napcat-qq`) calls `registerChannel({kind, title, project, resource_root, python, module, integration_directory, skill_directories})`. Its Python kind module gives the platform's id formats (`qq:<account>`, `qq:<bot>:<dm|group>:<target>`), how the adapter writes a real @ in inbound text and how her @ reaches it, the media hosts vision may fetch from by default, and the adapter's derived settings. Its adapter is the integration that her owner-granted `integration_*` tools develop and run, from the package's own development project. Its skill joins her skill directories. A platform's conversations live in a workspace named by its title.

`channelAdmission=automatic` admits authenticated, valid platform messages from previously unknown DMs/groups/members. The adapter derives `auto-dm-<id>` / `auto-group-<id>` route IDs; existing configured targets keep their routes. Core persists admissions in the existing `artifacts` collection and creates separate per-member channel workspaces without owner grants. An automatically admitted group member does not start another conversation or bump the group's authorization epoch. Removals/blocking revoke membership; old task epochs remain fenced. `explicit` requires configured enrollment. Both modes honor channel `blocked_senders` and `blocked_groups` before admission and outbox delivery.

Receipt projects to the target's real native QQ conversation before inference, including non-waking group activity. It uses the original durable input ID to deduplicate; an acknowledgment in `sink_receipts` permits projection retry after interruption without replaying execution. DSH requires a conversation's first visible entry to be the system head her agent writes on its first step, so until she has had a turn in a conversation its lines wait in that conversation's DSH inbox (next-step, the newest 40; older ones stay in Memory). Her first step there claims them right after the head, in arrival order and before the stage notice, which leaves out of its history what they already show. A line that arrives while that first turn is starting waits for its head. DSH lists a conversation in the sidebar from its first turn. The Web composer is view-only for QQ; native archive hides until the next platform activity.

All endpoints require:

```http
Authorization: Bearer <channel-token>
```

POST bodies are JSON objects, limited to 256 KiB. Unsupported envelope fields are rejected.

A channel kind that declares `ROUTE_KEYS` (`agent`) also takes a route key: `route-<route>.<hex>`, the HMAC-SHA256 of
`asuna-route-key:<route>` under the channel's token (`channels.route_key`). A route key posts events only as its own
route, claims only its own line's words (`/outbox` filtered by the route's target; group admin actions are never
handed out), and confirms only those (`/receipt`); every other endpoint, another route and another channel answer 403.
While she keeps that line closed, its claim returns `{"items":[],"line":"closed"}` and her words wait. At start the
host writes each such route's key to `<data>/private/route-keys/<channel>-<route>.json` (`url`, `route_id`,
`account_id`, `sender_id`, `key`) and removes keys of routes no longer configured. A route's optional `display_name`
(1–40 characters) is set on its person's identity at start.

### Receive an event

An inbound identity binds the channel, account, scene and platform event ID. When `occurred_at` is supplied, its value is part of that identity too: the same ID and send time is a redelivery, while the same ID at a different time is a new message. Adapters supply the original platform send time, or omit the field when unavailable; they do not substitute the time of forwarding. A reply resolves within its own scene and policy epoch to the newest matching inbound occurrence or delivered outbound receipt no later than the replying message.

```http
POST /v1/channels/{channel_id}/events
Content-Type: application/json
```

Direct message example:

```json
{
  "route_id": "authorized-dm",
  "account_id": "configured-account",
  "sender_id": "configured-sender",
  "event_id": "platform-event-id",
  "text": "Message text",
  "occurred_at": "2026-01-01T00:00:00Z"
}
```

`route_id`, `account_id`, `sender_id`, `event_id`, and `text` are required. `occurred_at` and `raw` are optional. Text is limited to 16,000 characters. The host derives person, scene, and target from the route; callers cannot supply a scope, task, or internal episode kind. Of `raw`, the host stores only the sender profile in `raw.asuna_peer` after checking it against the authenticated sender and group, the profiles of the people a group message @-mentions in `raw.asuna_mentioned` (each bound to an account in `mentioned_account_ids` and this group; they name those people in the group, as a speaker's profile does), the media block in `raw.asuna_media`, `raw.group_name`, and `raw.asuna_catchup` (`reason` `startup` or `reconnect`, `fetched_at`) on a line the adapter fetched from the platform's history after a gap; the platform event itself is not stored. A caught-up line was said at its `occurred_at`: the line she reads carries that time with 补读, and the history windows and the relevance gate count it from then (`caught_up.said_at`). Every QQ person, configured or automatically admitted, is `qq:<account>`.

Group events use the same endpoint and add `group_id`, `mentioned_account_ids`, and optionally `reply_to`. These values must come from the adapter's parsed platform event. Direct-message routes reject group-only fields. The host checks the configured group and member bindings. A group event wakes the character only under the configured mention and saved-reply rules; other authorized group messages can be persisted without starting a character turn.

Quoting: in a group her first message of a turn quotes the line that called her only when someone else has spoken since that line; her other messages never quote. Her `quote` tool (`how`: `source` | `none`, group turns that answer a line) overrides this for the turn, e.g. `none` for a bot command that must go out bare. Direct chats quote the line they answer (`publish._quote`).

A group message wakes her for one of these reasons. An @ of her account or a reply to a message of hers runs her full turn, unless it is a caught-up line older than 5 minutes (`caught_up.STALE_SECONDS`): then it is `wake_reason: catchup_mention`, through the gate, and a full turn carries `group_continuity_from_program.caught_up_from_program`. The others go through the relevance gate first:

- a reply inside a thread she was in;
- her name without an @ (her display name or the persona's `people.self_names`);
- the proactive rules of a group that opted in;
- a chain (below);
- an awaited answer: her newest delivered line in the group was addressed to someone — the people she @-tagged by label and the author of the line she answered (`channels.addressees`), waited on by default like a reply — and within `channels.AWAIT_SECONDS` (180 s; in her groups 90% of human answers come within about 3 minutes) one of them writes a line that @s and quotes no one. `await_answer` (`wait`: `no` turns it off for the turn; `yes` with `why` waits for anyone when the line is addressed to nobody). One look per line of hers (`wake_reason: awaited_answer`); her turn carries `awaited_from_program`.
- someone on her watchlist (`watches.py`): the `watch` tool (`op` `on` with `person` — a label, `#number`, name or id that names exactly one person in the conversation she is in — `hours` 1–72, `mode` `once` (default: the first time they speak, then done) or `burst` (again after 10 quiet minutes, until it expires) and an optional `why`; `op` `off` with the `id`) keeps at most 5 people in `watches`, one per person. A line from a watched person in any of her conversations sets `event.watched`; in a group whose line has no other wake reason it is `wake_reason: watched`, one look through the gate. In a private chat the line is already her turn. Her turn carries `watched_from_program`, and every turn `watching_from_program` (who, roughly how long is left, the mode, and the why only in a turn of the class she wrote it in). An expired watch is not a turn: the next turn's block carries one `ran_out` line on how often they appeared, once. The tool is offered in groups and private chats, and anywhere while the list is not empty. Nothing a watched person says is copied to another conversation.

The gate is one short request in a small per-group child session (`asuna-attend-…`, preset `asuna-attend`). It runs on the character route at a low effort, and compacts at about 5% of the context window. It reads only words:
- why she is asked;
- the speaker's label, notes and familiarity;
- the lines since she last spoke there (at least 10, at most 60 minutes back, at most 40 lines);
- how long ago that was;
- her public mood.

She answers 接话 or 不理 with a short reason. An answer in another shape is told so and asked again; after two repairs, or when the gate cannot answer at all, the message passes quietly. 不理 commits the episode before any recall (`processing_outcome: ATTEND_QUIET`). 接话 prepares her full context, says her reason in `attend_from_program`, and continues (`ATTEND_JOIN`). Every other message is stored without a turn.

A delivered line of hers whose platform read-back stored fewer parts than were sent (`segment_mismatch`: a QQ face, a quote, an @) carries `not_landed`, naming the missing part in words; the line stays delivered. In a group, a turn's history covers the same catch-up window, and never fewer than the last 12 lines. Every line says when it was said on her clock face: a platform line entering her conversation ends its label line with the local month/day and time (`[名字 #4] 10/5 08:19`), and a history row carries `at` in the same form instead of raw timestamps. A group turn also carries `pace_from_program` (versioned word tables in `places.py`, nothing advisory): when the last line was, when the current stretch of talk began (a pause of 30 minutes or more ends a stretch) and how much it holds, and the pause before it with how much has been said since the line before that pause. Whether an older line is still the topic is hers to judge. `deployment.reasoning_effort` sets the character route's effort per stage, where the model offers it: `attend` (default `low`) for the gate, and `group` for group turns. The local chat keeps the route's own effort.

The host persists accepted input before any retrieval or model call and returns:

```json
{"status":"accepted","episode_id":"ep-…","received_at":"…"}
```

An identical event for the same channel, account, route scene, and platform event ID returns `duplicate` without a second queue entry. On a peer line she has closed herself (a direct-message route of a channel kind that declares `PEER_LINE`), the host returns `{"status":"line_closed"}` and keeps nothing: the message is passed over, not queued for later. Reusing an event ID with conflicting identity or content is rejected. `accepted` confirms durable host receipt, not a reply or publication.

Adapters that normalize media may provide bounded metadata under `raw.asuna_media`. The host does not interpret arbitrary platform payloads. Media metadata and an image placeholder do not mean the character brain has seen the image; image reading is described below.

### Claim public output

```http
GET /v1/channels/{channel_id}/outbox?wait_seconds=25&supports=image
```

`wait_seconds` is capped at 25. The host atomically claims a queued public `SPEAK` message and returns its frozen target, text, publication ID, attempt ID, and optional platform reply target. Internal monologue, reasoning, traces, and tool output are never placed in the outbox.

`supports` is an optional comma-separated list of what the adapter can handle today (`supports=image,sticker`). An adapter that does not declare a capability receives text only. When a message carries an accepted image and the adapter declared `image`, the item also carries `attachment` metadata — `{artifact_id, media_type, sha256, size}`, never base64; the bytes come from the endpoint below. When the adapter did not declare it, the text still goes out and the message row records that the picture did not (`attachment_skipped`), so delivered history cannot later claim an image arrived that never left the host. A message that is one sticker is offered only to an adapter that declared `sticker`: its item carries `text: ""` and `sticker` — `{"kind": "custom"}` with the picture as `attachment` (send it as a picture marked as a sticker), or `{"kind": "market", "emoji_id", "emoji_package_id", "key", "summary"}` (send the store sticker by its ids, no bytes). Without `sticker` declared the row is failed with `CHANNEL_DOES_NOT_DECLARE_STICKER`. Her words may carry `[表情:名字]`, a platform face by name, for the adapter to turn into the real face.

The adapter sends only the returned text — plus the declared attachment, when the item carries one — to the returned target. Starting an adapter or claiming a message is not a platform receipt.

One reply may leave as several messages. When the persona model sets `speak.max_messages` above 1, a platform turn's context carries `speak_from_program`, a note telling her that her words go out as one message unless she writes the marker (`speak.split_marker`, default `[分条]`) where one should end. The core breaks the reply there, never inside a fenced code block and never on blank lines; pieces past the limit join the last message, and the local chat gets no note. Each piece is its own outbox item with `not_before` set by typing pace (`speak.chars_per_second`, clamped to `speak.min_gap_s`…`speak.max_gap_s`), and a piece is claimable only after the one before it settled: a failed or unknown piece cancels the rest (`CANCELLED_AFTER_FAILURE`). A picture rides on the first piece.

What she says is every text she writes in the turn, in order — text written beside a tool call included, since her conversation shows each as hers; with more than one, each is its own message where the persona allows several, else they join as paragraphs. A received line joins her conversation as it arrives, so a running turn sees lines that arrive between its steps. A line belongs to the first turn that had it in view (it reached that turn's model request): when that turn ends with speech or a deliberate silence, every such line still queued for its own turn is marked `absorbed_by` that episode and completes as `SEEN_IN_TURN` without a model call, so one line is never answered twice. A line that arrives after the turn's last request is not in view and gets its own turn. Platform turns are told both rules (`speak_from_program`).

### Fetch attachment bytes

```http
GET /v1/channels/{channel_id}/outbox/{publication_id}/attachment?attempt_id=…&artifact_id=…
Authorization: Bearer <channel token>
```

The same channel token authorizes this request. It returns the bytes of the one artifact that this publication's own claim declared, with `Content-Type` taken from the file signature. Only a publication currently in `SENDING` whose `attempt_id` matches the request may read it. The artifact must belong to that message's own scope, and the stored bytes are re-verified against the row's `sha256` before anything is written to the socket. `artifact_id` is optional and only ever narrows the request: a different artifact is refused, never substituted.

A row that records `attachment_skipped` is treated as never having declared the picture: its metadata stays on the row so delivered history can say the message was meant to carry one, and the byte endpoint refuses it with `ATTACHMENT_NOT_DECLARED` rather than handing out bytes for an image that never went out. A later claim that does carry the image clears that marker, so the flag always describes the current attempt.

Refusals are `403` with a code — `PUBLICATION_NOT_FOUND`, `PUBLICATION_ATTEMPT_MISMATCH`, `ATTACHMENT_NOT_DECLARED`, `ATTACHMENT_ARTIFACT_DENIED`, `ATTACHMENT_SCOPE_DENIED`, `ATTACHMENT_SHA_MISMATCH`, `ATTACHMENT_HASH_MISMATCH`, `ATTACHMENT_NOT_AN_IMAGE`, `ATTACHMENT_OVER_LIMIT`, `ATTACHMENT_MEDIA_TYPE_MISMATCH` — and carry no partial body. The adapter re-checks the digest and the file signature on its side. Neither side treats a successful claim as proof the image arrived: only a platform receipt says that.

### Post a group's member list

```http
POST /v1/channels/{channel_id}/members
Content-Type: application/json
```

```json
{"group_id": "group-id", "fetched_at": "2026-10-08T00:00:00Z",
 "members": [{"user_id": "10001", "nickname": "name", "card": "group card", "role": "member",
              "last_sent_time": 1791000000, "join_time": 1780000000}]}
```

The whole list of one group whose route the channel admits (not a blocked group), 1–5000 members, body up to 4 MiB. The host keeps `user_id`, `nickname`, `card`, `role` (`owner`, `admin`, `member`), `last_sent_time` and `join_time` in `group_members`, one row per group, replaced on each post; the answer is `{"status": "stored", "count": n}`. Refusals: `403 MEMBERS_GROUP_NOT_ROUTED`, `403 MEMBERS_SCENE_UNKNOWN` (no conversation for the group yet), `400 MEMBERS_INVALID`. A group turn carries `members_from_program`: the member count, the owner and admins by name, and at most 80 members (`context_budget.MEMBER_LINES`) — the people she knows there (by their label), the 50 most recently active, and anyone @-mentioned in the last 2 hours — each with how long ago they last spoke, plus how many are not listed and how old the list is. `find_member` (`name`, ≤ 20 characters; offered when the group has a list) finds members whose card or nickname contains it, at most 10, most recently active first, each by the label she copies to @ them. A member found who is not yet in `scene_people` is placed there with the list's names and `looked_up: true`, which her notes on that person say in words until a message by or about them arrives there; nothing is removed from `scene_people`. The rest of the list never enters it.

### Record a platform receipt

```http
POST /v1/channels/{channel_id}/outbox/{publication_id}/receipt
Content-Type: application/json
```

```json
{
  "attempt_id": "claimed-attempt-id",
  "status": "platform_accepted",
  "platform_message_id": "platform-message-id",
  "response": {"platform": "response"}
}
```

`status` is `platform_accepted`, `failed`, or `unknown`; `response` must be an object. `platform_accepted` requires a non-empty `platform_message_id` and records `DELIVERED` with `delivery_basis=platform_ack`. It means the platform accepted the message, not that a person read it. A matching receipt may be repeated idempotently; a conflicting attempt or terminal receipt is rejected.

If the send result cannot be determined, the adapter records `unknown`. A host restart converts an in-flight `SENDING` attempt to `UNKNOWN`. The host does not automatically claim it again. A later definitive receipt for that same attempt may resolve the state.

### HTTP outcomes

- `400` — malformed JSON, invalid size, or invalid field values.
- `403` — authentication, route, identity, capability, or receipt denied.
- `404` — unknown channel endpoint.
- `503` — host-side service failure; the host records a redacted diagnostic.

## Action capabilities

Action tool visibility is bound to the persisted task grant and route configuration. The action lane receives the DSH-native `skill`, `todo_write`, `web_search`, and `web_fetch` capabilities, plus Asuna tools allowed for that task. `web_search` is DSH's tool rebuilt from its exported parts (`registerWebSearch`) with 10 sources and a `detail` argument (`titles`: title, link and date only); snippets are capped at `search.snippet_chars` (300) and publication times are put on the conversation's clock from the session binding's `timezone`. Its backend is the cognition core's `asuna-search` provider on DSH's web service (`packages/cognition-core/src/search.js`), pinned by the installer, which tries `deployment.search.order` (default `searxng`, `gemini`, `exa`, `deepseek-official`) per query: SearXNG at most once per cooldown and resting after a failure or an all-blocked empty answer, Gemini with Grounding with Google Search (its cited pages as sources, redirect links resolved; resting after a 429 until the named quota refreshes), Exa through DSH's provider with a credential reference, other ids through providers registered on the service. A resting, unconfigured, failing or empty backend passes the query on; an empty answer is returned only when none had sources. Each search appends a log-only `asuna/web-search` event to the calling session. Settings and behaviour: [RUN_ASUNA.md](RUN_ASUNA.md#web-search). `web_fetch` is DSH's tool over the core's `asuna-fetch` provider (`fetch.js`): DSH's HTTP provider with a 5 MB body limit, HTML reduced to title and body without scripts, styles, SVG or templates, and a Cloudflare challenge (403/503 loading `/cdn-cgi/challenge-platform/`) returned as `WEB_HUMAN_VERIFICATION` ([RUN_ASUNA.md](RUN_ASUNA.md#web-fetch)).

Commands the worker does not write itself run under DSH's own sandbox: the Host wraps each one with `ctx.sandbox.confine` (dsh-sandbox-local — a restricted token on Windows, bubblewrap or Landlock on Linux, Seatbelt on macOS) in `workspace-write` mode, so it may write only its own folder: a task's folder for `sandbox_run`, the candidate for `development_run`, the output folder for a persona job, the data folder for an integration run. Reads and the network are not restricted. Which sessions may run commands at all is decided by the tools a task is given: `sandbox_run` is offered only to tasks from the owner's own scenes (her local chat and the owner's DM), and elsewhere her capability list says the action brain cannot run code there. Commands are native to the machine: `python3` is the worker's Python, and an argument `/task` names the task folder. `list_files`, `read_file` and `write_file` are done by the worker itself inside the task folder, protected sources read-only. The Host says at initialize whether it can confine; `deployment.sandbox.backend` is `auto` (default) or `none`. Without a Host sandbox, or with `none`, `sandbox_run`, the managed integration process, persona jobs and self-development are off: the tools are not offered, her capability list says these cannot be handed over, and the settings card's status line names the backend (`dsh`) or the reason there is none. On Windows the Host must be able to change permissions on the data folder (DSH grants each confined folder to the command and leaves that grant standing).

Asuna tools include scoped workspace operations, history search, structured discussion digest, `ask_character`, `report_progress`, and `read_image` when the action route declares image input. `read_image` is shared by both brains: her turn offers it when her own route declares image input and the conversation's recent pictures include one that can be pulled, or when her turn has pictures it may send (`image_artifacts_from_program`). Besides a message attachment ref, `read_image` takes the `artifact_id` of a stored image: one in the task's or turn's own scope, one she made herself (source `integration:`, from any scene), or one this turn was offered to send. Any other id answers `IMAGE_ARTIFACT_NOT_READABLE`, the same as an unknown one. This is how a picture is looked at again after it was drawn or before it is sent. Owner grants can add managed integration tools or self-development tools. A tool being registered does not grant it to every task. `import_integration_artifact` belongs to the managed integration group, not to the ordinary workspace group: a QQ task's grant never carries it. `generate_image` is granted to every task, from any conversation, whenever the integration is enabled and its profile has an endpoint named `image` (below).

`ask_character` asks her for a judgment that is hers and waits: her role session runs an internal turn (`think`, optionally `recall`, then `answer_action`) whose answer returns as the tool result. It creates no public reply, task or authority. `report_progress` leaves her a note without waiting; she reads it on her next turn.

## History, retrieval, and summaries

Conversation and memory records are scoped by scene and policy epoch. Every `recall` is audited (`recall.read`: what she asked, the sections asked, read and missing, the memories returned, the turn's kind and place). Memory indexing runs in the background over each conversation's scope and, once a round, her owner-private memories, 16 units per embedding request. When the embedding service refuses a request (HTTP 400, for example a unit longer than the model's context), its units are embedded one by one: a refused unit is embedded from its opening 400, 200 or 100 characters (`embedding_opening_chars`), and one refused even then is marked `embedding_status: REFUSED` for that embedding route and found only by lexical recall. An unreachable service marks nothing. History search reads authorized inbound messages and delivered `SPEAK` messages; it can return literal matches and, when available, semantic candidates. It does not turn a derived summary into a verbatim quote.

The explicit `history` tool also reads `direction: archived` rows under `archive:<scene_id>` for the current scene and its configured read links, with the same epoch rules. Archive rows share the live scene's `scope_key`, so conversation erasure covers them. They have independent sequence numbers and retain original text and timestamps; empty text can represent a media-only source. A result marks them `archived: true` and uses the person's existing roster label or their stored historical name without creating a people entry. Use explicit `since` and `until` dates for older archives; `window_days` is limited to 90. Archive rows do not enter recent context, familiarity, attention, recovery, publication, chunking, summaries, or automatic memory retrieval. Groups without a live scene remain unreadable until admitted. Raw wire text, unresolved reply context and attachment metadata remain under `legacy`; they are not attributed to a speaker as new prose.

Structured discussion digests use the scene-bound live history reader, without archived rows. They report their actual time and source coverage, preserve source references, and identify partial results rather than claiming an unread window was fully covered.

Background dialogue summaries process new messages in direct-message and authorized-group scenes after the summary boundary is initialized. They include inbound messages and delivered public `SPEAK` messages, and do not block the conversation. Each summary stores its source IDs, source window, participants, and per-speaker attribution. The participant list is computed from stored authors, not inferred by the summarizing model. Correction annotations resolve only against records in the same scene and policy epoch; unresolved references remain unresolved. When a later correction points to an earlier summary, the host appends a correction marker without rewriting the earlier summary text. A summary is evidence for a person only when its recorded participants include that person.

## What a turn carries

The program adds most of a turn's context by itself, so it also bounds it (`context_budget.py`, versioned). Nothing is cut silently: what a turn leaves out is counted and said, and stays readable through `recall`.

- **Per block.** Her mood lists every unsettled feeling and the strongest others up to 6, with `fainter` counting the rest; times are coarse words and event ids are 12-character prefixes (`feel` close/void accepts a prefix that names one event), so an unchanged mood reads the same from turn to turn. How to record a feeling is its own block, `how_to_record_from_program`. The clock is `clock_from_program`; how to write a plan is `schedule_control_from_program`, which does not change with the clock. Every time a model reads is on that clock (`local_time.py`): stored records keep UTC, and each turn context (`coordinator._deliver`), the gate's material, the action brain's program notes, and every role and action tool result pass `local_time.for_model` (the Host's `web_search` formats its publication times on the same clock), which rewrites each timestamp field (a key ending in `_at` or `_until`, or `at`, `until`, `since`, holding a full date-time) as `YYYY-MM-DD HH:MM` in the conversation's time zone (`schedule_rules.scene_timezone`). Free text is never rewritten; a sentence the program composes formats its own times (`local_time.stamp`), as the history search's lines do. The history search reads a `since` or `until` without an offset as a local time. Her ideas list open ideas before deferred ones (at most 20) and says how many more wait.
- **Her persona.** The system prompt (core header, persona and voice) is never cut. A section tagged `place:home`, `place:peer`, `place:group` or `place:dm` renders only in turns at those places (`visibility.place`: the owner's own conversations, a trusted home channel's line, a group, another direct conversation); a section without a place tag renders everywhere, and an unknown place is refused. The limit bounds the largest render over the places. Its limit is the larger of `render.budget_tokens` (default 6,144) and what the installed package's own persona and voice seeds render to plus a quarter, never above `render.max_window_share` (default 0.25) of the character route's context window. Tokens are estimated without a tokenizer: one per Chinese, Japanese or Korean character, a quarter per other character. Over the limit, the settings card and the memory tab show it in red, `render.over_budget` is audited, and an edit that would grow her persona or voice is refused (`PERSONA_RENDER_OVER_BUDGET`); edits that shrink it still apply. Seeds always load.
- **Her notes.** A note shown every turn (`inject: always` sections of a group's notes or a ledger, corrected sections left out) has a per-turn limit: 2,400 characters for a group's notes, 4,000 for each ledger. Within it the note shows whole, with `fullness` in words. Over it, the newest sections that fit show whole and the rest are named in `not_shown` by heading. A note more than twice its limit takes no new text (`NOTE_OVER_LIMIT`, said in words) until she shortens it, merges sections or tucks some away; shrinking edits always pass. Her understanding of a person, her character core and her current self are written whole and take at most 4,000 characters each. The persona and voice render has a fixed budget of 16,384 UTF-8 bytes by default (`render.budget_tokens`, which she may set up to 32,768).
- **Public words reach home only through her own review.** The recent experience a home heartbeat or self-improvement turn carries lists every line of her private conversations (`visibility.owner_private_scenes`) but only her own delivered lines from groups, other people's private chats and peer lines; a task from such a conversation keeps its headline, not its report. How the groups are going reaches home as words (`places_from_program`). Other people's words come home only through her ideas notebook (decided in self-improvement turns, with a reason) or a nightly `promote_memory`, which requires `why`, keeps it on the memory and audits `memory.promoted`. Every other home turn carries `elsewhere_from_program` (`places.elsewhere`): per other conversation in the last 6 hours (groups, others' chats, and her other home lines marked （家里）), what she herself did there in words (how much she said, how many of her pictures and stickers she sent, the tasks she handed over and their state), never anyone's words. Home conversations are her local chat, the owner's direct chats, and conversations of a channel kind that declares `HOME = True` (`dsh-peer`: the owner's own agents); QQ and any other platform kind are outside. In a home turn someone wrote (`external`: the owner, or a peer on a home line; not her heartbeat, plans or nightly turns, which have `visit`) she may be sent on an errand: the turn carries `errand_places_from_program` (her unblocked groups and configured direct chats outside home, by name) and the `errand` tool (`place`, `request` ≤ 500 characters, optional `exactly`). It queues a `visit` input there with intent `errand` (`visit:errand:<scene>:<event>:<call>`, so two errands in one turn are two), up to 20 a day, outside the visit limits; the visit records who asked (`author`, and `by` when it was not the owner) and `errand.offered` audits it. That turn is public, sees only that chat and `visit_from_program.request`, named as whose words they are (`exactly` asks her to relay them prefixed 「<who>让我转告」, 主人 for the owner), and may stay silent. An errand may carry one of her own pictures (`artifact_id`; that turn's `image_artifacts_from_program` always lists it, as a visit's does). Pictures are offered only where the channel kind carries them (`TEXT_ONLY = True` on `dsh-peer`); a group or anyone's DM other than the owner's gets only pictures she made (`outbound_media.own_only`). A `share_picture` visit does not wait for a quiet room; `start_topic` does. Integration (LAN device) tools are granted to the owner in the local chat and in their own platform DM (`integration.owner_dm`, by route and canonical person). From a home turn her `plan` create may name a peer line (`line`, as listed in `lines_from_program`): the plan is stored, fires and is changed in that line (`from_scene_id` records where she made it), and home turns list it under that line as `your_plans_there`. Home turns then carry `errands_from_program`: where she went, what was asked, and a program state word — never what anyone there replied.
- **Messages to the developer agent.** `developer_inbox.py` keeps one row per message in `developer_inbox`. A home turn (owner-private, not an outside note's turn) has `message_developer` (`level` `wake` or `note`, `text` ≤ 800 characters); at most 3 `wake` and 20 `note` in 24 hours (`DEVELOPER_MESSAGE_LIMIT`). The audit records `developer.message` with the level and length, not the text. Home turns carry `developer_inbox_from_program`: her last 5 messages of the past 7 days with how old they are and a state word (还没看 / 看到了，还没回 / 回了（回话在本机聊天里）). The developer agent reads unseen messages (`developer_inbox.unread`), marks them `seen` or `answered` (`developer_inbox.mark`) and replies in her local chat.
- **A Host taken away from outside.** A clean stop deletes the `host_leases` document; a Host killed from outside leaves this deployment's own lease behind. The next start finds it (`host_lease.DatabaseLease.left_behind`: the lease's expiry less its 90 seconds, so within one 30-second renewal of the last moment it was alive) and records one row in `host_stops` (`how` `killed`, `alive_until`, `back_at`). For 24 hours home turns carry `host_from_program`: 宿主上次是被外部终止的（不是正常停下）, when it was last known alive and when it came back on her clock face with the gap between, and a note that nothing ran in between and that nothing needs doing about it. Stopping a Host on purpose where a clean stop is not possible (a deploy that kills the process tree) is marked first with `python -m asuna.host_stops planned`: a stop within 10 minutes of the mark is recorded as `planned` and not shown.
- **Notes between her own conversations.** `notes.py` keeps one row per note in `notes`. A home turn (owner-private, not `consult`) has `pass_note`; a public turn has `leave_note`. Both take `to` (a place from `note_places_from_program`, or 家里 from outside) and `text` (≤ 300 characters); `pass_note` also takes `mode`. The program stamps the trust from the sending turn's session class: `trusted` from home, `untrusted` from outside. Home reaches its other home lines (`wake` by default, or `next_time`), any unblocked group (`next_time` by default; `wake` counts as a visit with intent `note` under `places.eligibility` and is recorded in the presence plan) and the direct chats an errand can reach (`next_time` only). Outside reaches home, which is always the local chat, and other groups, both as `wake`. A `leave_note` sharing a 20-character run (whitespace ignored) with someone else's line in that conversation from the last 2 hours is refused (`NOTE_NOT_OWN_WORDS`). The limits are 2 notes a turn, 40 a day, 6 a day from one public conversation to home, and 3 a day per pair of groups with 10 in all. Every refusal is `note.refused` and every note `note.sent` in the audit, with no text. A `wake` note to home queues the internal input `note` (`note:<scene>:<note>`, authorized as the scene's own person and allowed only in owner-private scenes); one to a group queues a `visit` with intent `note` (`visit:note:<scene>:<note>`, a scene tick with no channel envelope). Both go through `Chat.offer_internal`, so the input is durable before it is queued, recovered at restart, deduplicated, and runs after everything that scene already has queued. Nothing is appended to a running session. `note` is a core notice kind and its input is authored `asuna:internal`. The turn it opens carries `note_from_program`: where and when she wrote it, the trust words, the text, and a fixed note (from outside to home, the caution that it is a message and nothing with consequences happens in this turn). Its trigger is `note`. A home `note` turn drops the relationship, sender and understanding blocks. A trusted one has the tools of a scheduled turn there, without `visit`. An untrusted one has only `think`, `recall`, `read_image` (when she has pictures), `stay_silent`, `note_idea`, `feel`, `watch` and a reply by `pass_note` to the sending conversation. A turn opened by a note may reply once (`hop` 2, `reply_to`); the reply's turn may not write another. Every turn of a conversation lists notes written to it in the last 72 hours (`notes_from_program`, newest 5). An unread note shows its full text; a read one shows a 60-character excerpt. A note from outside shows only a summary in a home `self_development` turn, the turn that holds the development grant; every other home turn shows its text with the caution. Every turn also lists the notes written from there (`notes_sent_from_program`) with a state word: 送到了，还没读 / 读了，没回 / 读了，回了你 / 三天没读，过期了. A note counts as read once a finished turn has shown it. Public platform turns carry one sentence in `speak_from_program.one_self`. At home, a reason she recorded with `feel` outside says where (`where`), and so does a watch reason written outside. An idea in her notebook names the conversation it came from (`where`). A home turn may `feel` close or void a feeling recorded in a group. `delegate` and `message_action` are refused after 6 hand-offs in a row with nobody speaking (`delegation_depth`).
- **Nightly tidying.** Her settlement turn carries `notes_review_from_program` when notes are due: over or near their limit, or changed and not tidied for 7 days, at most 3 a night, most pressing first, each with its sections. Tidying is hers (rewrite, merge, tuck away, or leave as is); the program never edits or deletes her text.
- **The whole turn.** Past 48,000 JSON characters the oldest rows of a few lists go first — recent experience, promotion candidates, recalled memories, the topic thread, then history down to its last 4 lines. If the turn is still over (one huge message, row or block), the ceiling is hard: the longest text left is halved, repeatedly and never below 400 characters, keeping its start and saying how many characters went and that the original stays readable through recall. `trimmed_from_program` says what was left out or shortened. The worker records the turn's size as `context_chars` in its manifest and audits each trim as `context.trimmed`.
- **A conversation that no longer fits.** When a character turn in a scene's main conversation still fails with DSH's `CONTEXT_WINDOW_EXCEEDED` after DSH's own overflow compaction, the plugin reports it with the session's last `compaction/summary` text (`carry`), and the worker (`BusinessWorker.carry_session`) continues the scene in a new session: the scene gets a new `character_context` (`carried-<hex>`), the new main binding records `carry` (`from_session_id`, `summary`, `delivered`), and the old binding is retired with an explicit `character_context` and `successor_id`; `native.context.carried` is audited. The Host request `carry_session` prepares the new session as navigation does (title, workspace, nothing of the old session seeded), announces it to the sidebar and archives the old one once its agent is idle. Everything that resolves a conversation through `continued_session` follows the chain of successors; an action session started before the switch keeps its parent. The turn runs again once in the new session (`turn.carried`, with a resume note saying why), and its first notice carries `carried_from_program`: the summary, cut at 12,000 characters with the ceiling's marker, and a note that the earlier conversation no longer fit, that recent lines are in `delivered_history` and older ones in recall (without a summary, only the note). It is sent once, marked delivered when that stage succeeds. A carried session whose first notice never got through is not carried again: the turn fails as before.

## People in conversations

Identity is the account: an author's `person_id`, mapped to its canonical person by `canonical_persons`. That mapping is read from configuration only, so removing an alias immediately ends owner-private access for that entry point. A display name never decides who someone is. Each person gets a fixed label in each scene the first time they appear (`[name #n]`, stored in `scene_people`). The number never changes, so renames, members who share a name, and compaction neither merge nor split people. Names come from the verified platform profile on that person's own messages; a name the operator set in `identities.display_name` takes precedence for everyone except the owner. Names are NFKC-normalized, reduced to one line of visible characters, and stripped of the characters labels are built from (`[ ] 【 】 「 」 『 』 # < >`).

In the character's conversation, a QQ message is its label line followed by the message text indented by two spaces. A reply adds an indented `> 回复 <label>：<excerpt>` line. An @mention of a known person reads as that person's label, and a mention of her own account reads as her name. After the label, the program notes in words: a group owner or admin role, another member with the same or a look-alike name, a name containing the owner's label or her own name, and a rename within the last 24 hours. The owner's label starts with the persona's `people.owner_label` (core default `本机用户`) and is decided by account. Context blocks name authors by `speaker` label instead of author ids, and a recalled summary gives `who`, `about_current_speaker` and correction sentences. The summarizing model receives the same labels. QQ numbers stay in program data. Her context names conversations instead of giving their ids: `scene` is 本机私聊, 群聊「name」 or 私聊 with the person's label, and a row or memory from another conversation carries that conversation's name (a shared memory reads 不分场合, an owner-only one 只在私下). Scene ids, scope keys, policy epochs and platform message numbers are not in her context.

To @ someone in a group she writes their label (`@[name #4]`, or `@#4`; the owner's label may start with the owner word, and the whole label may sit in one more pair of brackets). The outbox turns it into the adapter's `@qq:<account>` marker when the item leaves the host; the stored message keeps the label, and a label that names nobody in the scene is sent as a plain `@name`. Two things in her speech are handed back in the same turn (`people.speech_problem`, detection only, nothing rewritten): a label opening a line without @ (开头的「[name #4]」不会 @ 到人…), and a label's number outside a whole label when it is someone in that scene (`@name #4`, `name #4`, a bare `#4`: 「#4」是程序给你认人的编号，群里的人看不到…, with that person's whole label to copy for an @ and the advice to drop # when she did not mean a person). A number that is nobody there, such as an issue number, passes. No label leaves the program: one written without @ whose number is someone in the scene is sent as their shown name (the name she wrote when the platform gives none, a real @ when neither is known); bracketed text whose number is nobody there is not a label and is sent as written (`people.outbound`). A stored `@qq:<account>` reads back to her as the label.

The history and discussion-digest tools take `person` as a label, a `#number`, an id, or a name. A name resolves against the scene's people (current, former and operator-given names, and names shown on their own verified messages); when it matches several people the tool answers with their labels and runs no query, and the filter is always by author, never by a name on a message. Results name writers by label and carry no author or person ids.

How well she knows the current speaker reaches her in `relationship` as words: `familiarity` is one level (the owner; known, when she has written an understanding of them or answered them many times; regular; met; new), computed from the owner's account, her written understanding, the turns in which she answered them and the lines they wrote, across every conversation of the canonical person. Nothing a message says raises it. A persona words each level and gives its `stance` in `people.familiarity`. What she has written about them comes in two layers (`understanding.py`). `person` is one record per canonical person (`relationship:<person>|person`), read in every conversation where she meets them: `first` always says 这只是他的一部分，不是他的全部 and, when she keeps a here layer for them in other conversations, how many; `text` is what she wrote; `written` names the conversation it was last written in and how long ago (each revision keeps `origin`: scene and time). `here` is the record for this person in this conversation (`relationship:<person>|scene:<scene>`, shared with a configured linked entry as before), read only there. No record is seeded: everyone starts with none, which reads as 你还没写过这个人在哪儿都成立的那一层 and 你还没写过他在这里是什么样. `understand_person` takes `layer` (`person` or `here`, required; `UNDERSTANDING_LAYER_REQUIRED`) and the layer's whole new `body`; each layer is written at most once a turn (`understanding_update`, `person_understanding_update`), from any conversation, with the same source registration. The program does not filter what goes where: `understanding_update_from_program.target` gives her three questions to ask first (does it hold in another group; would saying it somewhere proper make the person uncomfortable; did they say it, did she see it, or does she infer it). Erasing a memory takes back every person-layer revision citing a source from that conversation; the record falls back to the newest revision before it, or is removed.

## Her place in a group

Her own role in each group reaches her in words in `your_place_from_program`: 群主, 管理员, 普通成员, or not yet known. The adapter asks the platform for the logged-in account's own role (cached for ten minutes) and sends it in `raw.asuna_self`. The host keeps only a valid role, and only on group events.

Where she is the group's owner or an admin, the block also tells her how to use her `group_action` tool:

- `kind`: `mute`, `unmute`, `recall` or `kick`;
- `who`: a label or `#n`;
- `duration`: 1分钟, 10分钟, 1小时 or 1天 (mute only);
- `which`: 这条 or 他刚才那条 (recall only);
- `reason`.

The program refuses any of these, by name:

- she is not an admin;
- the route sets `admin_actions: false` (admin actions are on by default);
- the target is unclear or unknown;
- the target is the owner, herself, the group's owner or another admin;
- a mute without a duration;
- there is no recent message to recall (recall takes the message that woke her, or the target's last line within 10 minutes);
- more than 6 actions in an hour in that group.

An accepted action becomes a `group_action` artifact. The outbox hands it to the adapter before any message, and the adapter calls `set_group_ban`, `delete_msg` or `set_group_kick`. The platform's answer arrives through the same receipt endpoint and updates the artifact (DONE, FAILED or UNKNOWN). An action interrupted while it was being sent becomes UNKNOWN and is never retried. Her words for the result say 已交给平台，等确认 until the platform answers; the account and message numbers stay in program data.

`group_notes_from_program` shows her own notes about the group: who is who, its customs, how she acts there. She writes them from that group's own turns with `write_document` and `doc: "group_notes"` (`append_section`, `replace_section`, or `set_tags` to tuck a section away with `inject: "on_demand"`). The program maps that name to the group's document and keeps its sections public to that group, also when she tidies them from home by the document name her nightly settlement lists. The block shows the notes within their per-turn limit (see What a turn carries).

## Media and image reading

An adapter may normalize non-text segments into bounded `raw.asuna_media` metadata. The host preserves placeholders and does not treat them as visual input. The action task receives a bounded list of image attachments from its own scene and policy epoch, plus images from scenes it may read only through a configured cross-scene read link; every entry carries `scene_id` and `linked_scene`, so the listing states where each image came from.

The action brain can call `read_image({"ref": "…", "max_bytes": 4194304})` when `executor.input_modalities` includes `image`. The reference selects an attachment already visible to that task; it cannot widen the read scope. That scope is recomputed from configuration at call time (`context_links` or route-level `read_scenes`, own scene first), so deleting the configured edge returns to own-scene-only, and a linked scene missing from the database or sitting in another policy epoch is simply not scanned. Bytes pulled from a linked scene are still stored under the calling task's own scope key. URL fetching requires an allowed host and safe redirect, enforces a byte limit, and accepts PNG, JPEG, WebP, or GIF data identified by file signature. An animated picture (GIF, WebP or APNG with more than one frame) reaches the model as a PNG contact sheet (`animated.py`): the moments at even intervals across one loop (`CELLS`, 9), neighbouring moments that look the same merged into one cell, each cell labelled with its order and its time in the animation; transparent pixels show light grey. The result's `animated` words say how many frames there are, how long one loop takes and whether it repeats, how much the picture moves, how many of the frames left out differ visibly from their nearest cell, whether there is fast back-and-forth flicker (frames of at most 60 ms alternating), a frame that holds most of a loop, and that the sheet is not the animation. The stored bytes stay the original. One too large to split (over 1,500 frames or 300 million decoded pixels) or that fails to split is passed as it is, and `animated.error` says only its first frame is seen. An optional local image directory can also be configured. Pulled bytes are stored through the scoped blob store and passed to DSH as a durable image attachment. The stored tool receipt contains metadata and blob references, not base64 image bytes.

The character brain has the same tool. Her turn offers `read_image` when `character.input_modalities` includes `image` and the conversation's recent pictures — the same window, fences and linked scenes the action brain reads — include one that can be pulled. The call runs in her turn's scene and scope, stores bytes the same way, and becomes an image attachment in her turn; the episode's `tool_calls` and the audit keep only the receipt. A full group turn brings pictures by itself (`role_tools.turn_pictures`): the pictures on the line that started it, then photos (not stickers) from the 6 lines before it, at most 2 in all; each is pulled like `read_image` and becomes an image part of the turn's first message, and `pictures_from_program` names each `ref` and its line (触发这一轮的那条 / 前面第 n 条; an animated one also carries its `animated` words). One that cannot be pulled is left out. A platform line entering her conversation names its pullable pictures under the text (`（图 ref：att-…）`), and her media note tells her to look herself, or to put the `ref` in the brief when she hands picture work to the action brain. Looking does not wait on sending: in an owner-private turn where none of her pictures can be sent (her local chat has no channel route), her newest own pictures — at most 5, ids and when — are listed as `your_pictures_from_program`, and `read_image` comes with them. A picture the model refuses does not end the turn: DSH stores a looked-at picture in the conversation's session log and rebuilds every request from it, so when the provider refuses a request from one of Asuna's sessions as invalid (`INVALID_REQUEST`, e.g. a WebP its server cannot decode) while the conversation still sends pictures, the plugin records one DSH `image/offload` decision for every retained picture there — they become DSH's "image omitted" placeholders from then on — and the request is tried once more (`image-refusal.js`). A refusal with no picture left to omit ends the turn with the provider error.

The default byte limit equals the 8 MiB hard limit: QQ photos are routinely 4-6 MiB and DSH re-encodes request images toward a 1 MiB target, so blocking at pull time would be an Asuna fence, not a route capability. Host allowlists, timeout, local directories, and insecure HTTP policy are configured under `vision`; the allowlist defaults to the multimedia host this deployment has actually received. Unsupported routes, disallowed sources, and fetch failures return real error codes, and a non-2xx response carries the server's bounded reason with any temporary `rkey` redacted; placeholders are not reported as viewed images. Download URLs are re-read from the stored message at pull time and are never embedded in the listing or truncated. Durable image references enter the native attachment pipeline; request image limits and pricing belong to the selected DSH provider. There is no Asuna token proxy.

A picture the owner attaches in her local chat stays in her conversation, so a character route that declares image input sees it directly; past the route's image budget, DSH's image offload — mounted once by its base profile for every session; a second mount in a preset breaks session resume — swaps the oldest for placeholders and retries. The plugin also reads each attached picture back from DSH's attachment store (at most 8 per input) and passes it with the input; the host stores it as an image artifact in the local chat's scope (source `local-upload:<input id>`, once per input) and records it on the input row as `raw.asuna_media` with `origin: local_upload`, its placeholder leading the text — so history and recall keep it after compaction, a picture-only message is a valid input, and a picture that could not be read is recorded as such. Her turn's media note says the picture is already in the conversation; the action brain reads it by `ref` from the blob store (`pulled_via: blob`, no host allowlist, nothing stored twice). Only the program's own local input can name such an artifact: a platform message carrying the same fields is not pullable from the blob store. As her image in the local chat it can be attached in the owner's linked QQ DM, never in a group.

### Sending an image with her words

A turn may also carry an image out. When the scene is the owner's own private conversation (`session_class=owner_private`) and its channel route targets a `dm`, the context gains `image_artifacts_from_program`: the image artifacts this turn may reference, each with `artifact_id`, `sha256` and `size`, plus a note that these are program-held artifacts and not file paths. Only then does her turn offer the `attach_image` tool (`artifact_id`, `why`): one picture per turn — calling it again replaces the first — and only an `artifact_id` from that list. A direction this version does not open, an artifact that was not offered this turn, bytes that are not an image by file signature, or a size over 8 MiB is refused as a tool error with its code and reason, and she can still finish the turn. A turn that ends with `stay_silent` and has no words sends no picture. In a group she is in (a group scene with a group route), the list holds only pictures she produced herself — bytes from her own generator (`generate_image` or `import_integration_artifact`, source `integration:`), from whichever of her scenes they were made in — never a picture someone sent her; she decides whether and where to send one, always all-ages. The tool and the attachment endpoint refuse anything else in a group with `ATTACHMENT_NOT_HER_OWN`. Other people's private conversations, and a private scene routed to a group, are refused deterministically instead of silently degrading into text whose receipt reports a picture as delivered.

Her credentials (`credentials.py`): a credential is a name, a note and up to 6 environment variables. Values live in DSH's credential store, one record `asuna-cognition-core/<name>` (kind `grant`, payload `{note, env}`), read and written by the Host on the worker's `credentials` request. At home (owner-private `external` and `task_feedback` turns) the character brain's `credential` tool files one (`keep` with `name`, `note`, `env`; again under the same name to replace it) or removes it (`drop`); the value passes her model in that call only. Home turns and home tasks list `credentials_from_program` / `facts.credentials`: names, notes and variable names, never a value. Only a task from home may use one: `sandbox_run` with `credentials` (names) sets those variables for that one command (`CREDENTIALS_HOME_ONLY` otherwise). Every stored value, as written or URL-encoded, is replaced by `[凭据已隐藏]` in tool results and receipts, in her briefs and messages to the action brain and in its reports. A script that holds a value could still send it out over the network; the protection is that no model holds it. The core skill `asuna-credentials` teaches the rules, including using someone's account only for what it was granted for.

Stickers and the platform's own faces. A sticker is a picture someone sent *as a sticker* — still or animated, or a store sticker — never a photo; the adapter marks it on the media item (`sticker: custom|market`), and for items stored before it did, the platform's channel kind tells from the item (`sticker_of`). A platform line names its stickers under the text as `（表情包 ref：att-…）` and its other pictures as `（图 ref：…）`. In a conversation whose platform sends stickers (`channel_kinds.sends_stickers`), her turn carries `stickers_from_program` — her shelf by name, each with her note on when it fits, how often she has used it in words, the shelf's count and fullness word — and `faces_from_program` — the face names people there used lately — and offers the `sticker` tool: `keep` (a sticker `att-` ref from this conversation, or the `blob-` id of a picture she produced; a `name` of up to 12 characters and a `when` of up to 40), `drop` and `rename`. A photo is refused (`STICKER_IS_A_PHOTO`), so are a name or sticker she already keeps (the same picture with other metadata counts as kept, `STICKER_ALREADY_KEPT`), and a full shelf (`STICKER_SHELF_FULL`, 60, `context_budget.STICKER_SHELF`). Keeping a custom sticker pulls its bytes once into `global-safe` (source `sticker:<message>`); a store sticker keeps the platform ids it is sent again by. To send one she writes `[表情包:名字]` in her speech: it leaves as a message of its own, one per turn, its row keeping the token as text and carrying `sticker` (and, for a custom one, the picture as `attachment`, which the attachment endpoint serves to any conversation that takes stickers because it is on her shelf). `[表情:名字]` inside her words is a platform face; the adapter turns a known name into the real face. Her speech is sent back in the same turn when it names a sticker she does not keep, more than one sticker, a face name the platform does not know, or either where stickers cannot go (her local chat). At home `stickers_from_program` lists the shelf for tidying, each sticker with a picture carrying its `ref` (its artifact id), which `read_image` takes, and the nightly settlement carries `stickers_review_from_program` once a week (or whenever the shelf is 80% full): the stickers kept two weeks and never sent, or not sent for two weeks, at most 6. Rotating is hers — the program never drops one. The candidate pool: every sticker posted in a group is saved as it arrives (`stickers.pool_seen`, off the input path; bytes in `global-safe`, source `sticker-pool:<message>`) into `sticker_pool`, merged by picture or store id with how often and where it was seen, skipping what is on her shelf; past `POOL_MAX` (30) the least recently seen leave. Her nightly settlement carries `sticker_candidates_from_program` (the 8 most posted) and a group turn the ones posted there in the last 2 hours (4); wherever her shelf is, `sticker` `pool` returns the same list as the nightly one with the pool's count, and the turn then offers `read_image`. Each `candidate` is an artifact id she may `read_image`. `sticker` `keep` with `candidate` puts one on her shelf only if she looked at it in that turn (`STICKER_CANDIDATE_NOT_LOOKED`), under her name and note; it then leaves the pool. Stickers she knows: `sticker_memory` keeps, per persona and for good, what she called a sticker, keyed by a fingerprint — a store sticker's `market:<emoji_id>`, or `md5:<hex>` of a picture's bytes, which the channel kind can read from a media item without fetching it (`channel_kinds.sticker_md5`; QQ names the file by it) — and by its picture (`picture`: `img:` and the SHA-256 of its image data without metadata, `stickers.picture_key`; JPEG APP segments and comments, PNG text, time, EXIF and pHYs chunks, WebP EXIF, XMP and VP8X chunks are left out). A posted custom sticker whose md5 is unknown is downloaded once by the program as its line enters her conversation (`PICTURE_FETCH_SECONDS`, 5 s; a failure leaves it unknown) and matched by its picture; a match adds that md5 to the memory's `aliases`, so a copy re-sent with rewritten metadata is known and the next one needs no download. Every sticker she keeps is known by its name and note (rename updates it; dropping it does not forget it; at startup `remember_shelf` covers the shelf as it is, pictures included), and `sticker` `remember` (an `att-` ref or a `candidate`, with `name` and `when`) records one she looked at in that turn and does not want to keep (`STICKER_NOT_LOOKED`, `STICKER_NO_FINGERPRINT`); remembering again replaces her words. When a known sticker is posted, its line reads `（表情包 ref：att-…，你认得：「名字」，她的说明；在你架子上|你收过又放下了|你看过没收）`, also when the picture itself can no longer be pulled. A known sticker is never a pool candidate, and a candidate she remembers leaves the pool. `read_image` of a sticker adds a `sticker_note` pointing at `remember` and `keep`. A claim that does not declare `supports=sticker` gets no sticker row: it is failed with `CHANNEL_DOES_NOT_DECLARE_STICKER` rather than sent half.

Two things put images on that list: bytes this scene already stored (`read_image`, and `import_integration_artifact` when the imported bytes turn out to be an image), and images registered in **one other scene belonging to the same person**. That exception exists because an import runs only in the local owner task (and a picture is often made there) while the turn that speaks the picture is usually the QQ private chat, and both entries are the owner's own private space. `outbound_media.image_scopes` computes the readable set from configuration at read time: this turn must be `owner_private`, the peer scene must be a `dm` whose canonical person is the same owner, and the two scenes must be joined by a `context_links` / route `read_scenes` edge. Between two owner-private scenes of one person the edge counts in either direction — neither end can downgrade owner-private data into a public session, which is what `visibility.without_link_downgrades` exists to refuse. Groups, another person's scenes, unlinked scenes and public turns never extend the list, and offered items that came from the peer scene say so (`from_linked_scene`, plus its `scene_id`). The attachment endpoint recomputes the same list from the publication row itself (scene, the person on its route, session class): a caller cannot pass a scope, and deleting the configured edge returns the fence to own-scene-only without any code change.

An accepted attachment writes metadata only, on the first `SPEAK` row (`attachment`); bytes stay in the scoped blob store and travel over the attachment endpoint above. Delivered history then shows the picture as something she sent, with its media type and size, and says so differently when the adapter never declared image support, when the platform receipt's attachment evidence does not match the stored digest, or when the row was never delivered. Text-only messages keep their previous shape exactly: no attachment slot, no extra wording, in her context and in history search results.

## Schedules

The host uses DSH's native scheduler; it does not run a second host timer wheel. Scheduling, updating, or cancelling a plan is a character decision in the authorized scene. A due plan re-enters that scene and asks the character to decide what to do. A due event is not new authorization and does not mean its requested work has completed. Plan status and policy epoch are checked before dispatch. In a platform conversation (a group or a DM) the due plan is a core notice, not a platform input: it carries no channel envelope, so it is never re-checked as a member's message or shown in that conversation's session as one; it wakes the conversation as a scene tick, the plan's person must still be a member of the route (`SCHEDULE_ROUTE_REVOKED` otherwise), and what she says goes out on the conversation's own route, with no platform message to reply to.

Asuna reuses an installed DSH Schedule service. When the Host has none, it mounts that same service once, unless the `asuna-cognition-core` setting `mountSchedule` is `false`; then plans, heartbeat and settlement are off. By DSH design the `schedule_*` tools of a mounted Schedule are visible to every root agent in the Host; Asuna's role and action presets restrict their own tools.

Her rhythms — the heartbeat (`presence`), nightly settlement and self-development — are plans the program owns: they never appear in her plan list, so her plan tool cannot cancel or retime them. The heartbeat runs at home, in the owner-private scene named by `persona_runtime.<persona>.heartbeat_target`, when her persona model also sets `heartbeat.enabled`; only the owner turns it on or off (a package may default `heartbeat.enabled`, never declare it as a policy key). Its pace is hers through core policy keys: `heartbeat.every_min` (15–240; anything outside is clamped), `heartbeat.min_gap_min` (0–720), `heartbeat.skip_in_sleep`, and `heartbeat.pause_min` (0–720: beats skip until then and resume by themselves; 0 resumes now). Before any model call a beat is skipped, with one counting audit, when a role turn is running or queued at home (the action brain working on a task does not count), during her pause, within `min_gap_min` of her last internal turn at home (heartbeat, settlement or self-development) unless something reached her since — an inbound message that woke her in any routed scene, or a finished task — in her sleep window when she chose `skip_in_sleep`, or after 24 beats that reached the model on that local day. A watchdog checks after every turn, at every settlement and self-development dispatch, and every five minutes from the host's existing watch thread: a heartbeat with no dispatch for two beats plus five minutes is audited as `rhythm.heartbeat_missed`, its native record replaced, and her next beat tells her it was reconnected. The five-minute check also recreates a native record deleted elsewhere and restores her pace on one retimed elsewhere (audited as `rhythm.retimed` with `drift`).

The owner sees her reminders in DSH's own task page (the Automation tasks entry; `@deepseek-ai/dsh-client-ui-schedule`, mounted by the core without the optional bundle's time context, which would show the browser's zone to her turns). Each task is named as she reads it — her plan's own words, or for her rhythms Heartbeat, Nightly settlement, Daily self-improvement, and Night self-improvement check for the 10-minute tick that only decides whether a night stage is due — with its next run and delivery records. A one-off reminder leaves the page once it has fired, as a cancelled one does (its plan keeps the record); a start removes any left behind and renames a task whose title no longer matches her plan's words. The rhythm names and the scheduler session's title (Asuna schedules) are in the language of the browser that last opened the Web UI (`ui-language.js`: the client reports its active language through `uiLanguage`, again on a switch; the words are the core's `locale/<language>.json` `asuna.titles`, English for a language without a file; the choice is kept in `<data>/ui-language.json` for the next start). Asuna's agent presets (the core's and each persona package's role preset) are rows of `@asuna/cognition-core/preset`, which declare `names` and `descriptions` per language and register, at start, the words of that saved language (English when it has none); a switch of language shows in preset names at the next start. The scheduler session logs what DSH changes on a record (its next target after a delivery, an edit in that page) so the worker reads each record as it is now. `/heartbeat` in any session gives her one heartbeat now through the same path, skipping the gates (audited as `presence.forced`, and her beat says it was knocked early), and replies with the next scheduled beat; it creates no model message.

A heartbeat at home, or a plan of her own that comes due there, may send her on a visit. With `heartbeat.visits` on, her presence turn — and a `scheduled` turn in an owner-private conversation — carries `places_from_program`: each routed, unblocked group as words only — how busy it is and when the last line was, how many people spoke in the last hour, when she last spoke there, her last visit and what came of it, whether someone called her since she last spoke, her notes' headings, and whether she can go now, and the time there (`their_time`) when she gave the group a time zone — plus `last_visits_from_program`. In a home turn `place_timezone` gives a group its time zone (`op` `set` with `place` and an IANA `timezone`, `clear`, or `list`: every group, its zone or 没设, and the time there; a set answers with the time there, so a wrong zone shows at once); it is stored on the scene (`timezone`), decides that group's night and is the time zone of plans she makes there; an unset group keeps the Host's clock. No line anyone wrote crosses. The `visit` tool (`place`, `intent` = `start_topic` | `share_picture` | `check_in` | `write_notes`, optional `topic` ≤ 80 characters and `artifact_id` of a picture she produced) is offered only there, up to `heartbeat.visits_per_beat` times a turn (1–3, default 1; hers to set, shown as `places_from_program.this_beat`; the cooldown still stops a second visit to the same group), and is refused with the reason when the group is not open to her now: today's `heartbeat.visits_per_day` (0–8, default 4) used up, night there (the route's `proactive` quiet hours, or 23:00–08:00, on the route's offset, else the group's own time zone, else the Host's clock), within `heartbeat.after_own_min` (30–1440, default 360; doubled when what she last said there got no answer) of her last speech or visit there (a visit whose turn there has not run yet is refused as 已经出门去那个群了，那边那一轮还没跑完, and its outcome reads 那边那一轮还没跑完，结果还没出来), or — for `start_topic` and `share_picture` only — someone spoke within `heartbeat.quiet_min` (0–240, default 30); going to look or take notes while people talk is fine. A visit whose input failed never got there: it comes home as such and spends neither her day nor the group's wait. An accepted visit queues an internal `visit` input in that group (`visit:<scene>:<beat event>`, wake reason `visit`). It carries no channel envelope — it is her own moment, not a platform message, so the group's session never shows a member saying it — and wakes as a scene tick; what she says goes out on the group's own route. the turn is `public` because the scene is, titled "Her own visit", and sees that group's catch-up, her group notes, her produced pictures and `visit_from_program` (why she came, her topic, the room in words, whether anyone called her) — no relationship, speaker, rhythm, cross-scene experience or home places. It has no `visit` tool and no development grant. What she says there counts toward the per-group caps of unprompted speaking (`proactive`).

A chain calls her in any of her groups, whether or not unprompted speaking (`proactive`) is enabled there: when the newest line ends a run of the same text — or the same picture or sticker, by file, or store sticker, by id — from at least three different people, with no line of hers inside it, the line is woken with reason `chain` (`group_context.chain` = what, how many people, whether it is media). Only the night quiet hours (the route's `proactive` block even when it is off, else 23:00–08:00) and a busy foreground hold it; the burst, cooldown and hourly gates do not, because a chain is fast. One chain calls her once (`proactive.chain.woke` on the line); her own line ends the run. The relevance gate asks 接话 or 不理 with the reason in words, and her turn carries `chain_from_program` (what, how many people, how to send the same thing: copy the line, or keep the sticker by its ref and send `[表情包:名字]`). Whether and how she joins is hers.

## Managed integration and self-development

The managed integration runner is available only to the configured local owner profile. The adapter's code lives in its channel package and changes only through the development tools. `integration_test` runs a frozen, read-only `/app` copy of the development candidate's adapter with separate writable `/data`; `integration_start` enables a frozen copy of the published adapter as a managed process, and host restart restores the then-published adapter. Unpublished edits never run as the managed service. `integration_status` reports process state and bounded logs, not platform connectivity or delivery. `integration_stop` stops the managed process and disables host restart restoration.

A started service (`integration_start`) is restored on every start; `integration_stop` keeps it stopped. An enabled integration whose adapter serves a channel (`adapter_config.host.channel_id`) starts that channel's resident command (its kind's `SERVICE_ARGV`) from the published adapter by itself, when it was never started or stopped before; a failure shows in `integration_status`. Integration processes run under the Host sandbox like any command: they may write only their data folder, and reach the configured endpoints directly at each device's own address (the adapter settings may still name an endpoint by its configured local `port`; the run's settings carry the device's address instead). Their commands are argument arrays, not host-shell strings; `/app`, `/data` and `/integration/config.json` in an argument name the run's frozen adapter copy, its data folder and its settings (also `$ASUNA_INTEGRATION_CONFIG` and `$ASUNA_INTEGRATION_DATA`). Connection credentials come from the local integration profile and are not copied into ordinary task files. A test run (`integration_test`, unpublished adapter code) uses the real settings and can act on a platform for real (the integration tools are owner-only); messages are meant to leave through the outbox and the published adapter started with `integration_start`. Each run's copy of the adapter is removed when it ends; only the service's copy is kept. An endpoint marked `"tls": true` is reached over TLS without verifying the device's certificate; `"read_only"` is a description of the device, not enforced.

`import_integration_artifact` reads one artifact over one of those configured endpoint aliases: the model supplies the alias and a path, never a URL, host or port, and the fetch performs a single HTTP/1.1 GET without following redirects. The host writes the bytes into the task workspace bound to this action at a relative path — existing files are kept unless `overwrite=true`, protected inputs are never written through, and the size cap is 4 MiB (1 MiB by default). The result reports the relative path, absolute path, byte count and SHA-256 actually written, or the real failure: unknown endpoint, URL rejected, path outside the workspace, target exists, over limit, HTTP status or transport error. When the bytes actually written are a PNG/JPEG/WebP/GIF by file signature (not by file name or `Content-Type`), the host additionally registers them as an `image` artifact in the scope this task is bound to — never a scope the model names: `kind=image`, `storage=gridfs`, `state=DONE`, media type from the bytes, and a SHA-256 the host recomputes and re-reads itself, with the result then carrying an `artifact` block (`artifact_id`, digest, size) so a later turn can send that picture out. Bytes that are not an image change nothing: the result keeps exactly its previous field set and no artifact row is written. A registration that cannot happen (a scope the store does not know, bytes over the 8 MiB outbound cap, a storage error) never turns a completed import into a failure — the reason is reported honestly under `artifact`. Offline: `python3 tools/integration_import_offline_check.py` and `python3 tools/outbound_image_offline_check.py`.

`generate_image` draws one picture with the endpoint aliased `image`, for any task: the integration tools stay owner-only, and this tool is the one fixed sequence of that service's agent API (`project-comfyui-agent/v1`). The model supplies a prompt and a few choices — an optional ready text-to-image `workflow` id (otherwise `POST /project/resolve` picks one with `content_mode=sfw`, optionally for a `style`), `negative_prompt`, `width`/`height` (64–2048, multiples of 8), `seed`, and `options` limited to `steps`, `cfg`, `sampler_name` and `scheduler` that the workflow's `parameter_schema` declares — never a request, URL or path. The host runs `integration_image.py` as a trusted one-shot integration run that knows only the `image` endpoint and carries no adapter settings: it checks the workflow, `POST /project/generate` with `batch_size` 1, polls `GET /project/jobs/{prompt_id}` and fetches the first `/view` output (at most 8 MiB). The runner lock covers only the launch, so integration tools, status and stop do not wait behind a generation. A job still queued or running when `timeout` (default 180 s, at most 300) runs out is reported with its `prompt_id`; calling again with `job` collects it without drawing again. The host verifies the byte count and SHA-256, writes the picture into the task workspace (a new file under `images/`, or `target_relative_path`; never over an existing file) and registers it in the task's own scope with source `integration:image:<view path>`, so it counts as her own picture. The service's refusal (HTTP status and its `error` object) is returned as it was. `workflows=true` draws nothing: it lists the ready text-to-image workflows with the service's own guidance for each (prompt style and structure, quality prefix, best for and not for, recommended size, an example prompt), and every drawn result carries the same guidance for the workflow that drew it. Without a named `workflow` the service picks a generic anime one, and some workflows (such as Qwen-Image) are chosen only when named, so the brief says to list first. Nobody has seen a drawn picture until a model looks: the result and the brief say to call `read_image` with its `artifact_id`, compare it with what was asked and draw again when it is wrong. The task brief names this tool first for pictures; public generators reachable by `web_fetch` stay allowed, but their pictures cannot enter the workspace and can only be linked. Offline: `tests/test_image_generation.py`.

`private_words` (both brains, every conversation and task, except a turn opened by a note from outside) keeps the deployment's list of words that point at real people and places (`private_words.py`): `op` `add` (`category` person, group, account, site, host, email or other; `word`; `why`, one line of at most 200 characters; the same word again replaces its entry), `remove` (`word`, exactly) or `summary` (entries per category). The list is `<data>/private/personal-words.txt` (`ASUNA_PRIVATE_WORDS` names another file), one `category|word|why` per line.
