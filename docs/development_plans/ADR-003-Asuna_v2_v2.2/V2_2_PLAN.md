# V2.2 开发主计划：QQ 作为正式输入通道

2026-09-21 入口修订：当前正式交互与开发验收统一走 Web，CLI 仅限显式 debug；本文件 QQ 目标仍是后续计划。适用规则见 [CODEX_START.md](CODEX_START.md) 的入口修订。

## 0. 本轮不是重新实现双脑

**既有分工不变**：Gemma 是有界、由代码推进的角色主体；Qwen 是更自主的行动脑；宿主负责信息到达、范围、调度、持久记录和发布。小满的语气、价值与私人理解不能成为大量 QQ 调试日志的附属品。

用户分享裸 DSH 原型，是因为它与行动脑使用同一 Qwen3.8 Flash 本地部署。这些错误是现实风险样本，而不是证明新架构必然失败。解决同类问题要落到正确性边界，不能只追加“记得不要犯错”的 prompt。

本包将之前讨论的 V3 中与 QQ 日常使用直接相关的最小部分纳入 V2.2：原生事件入口、多用户／群现场、基础话题关联、DSH 定时自主活动、可靠记忆和可选总结。**不等于建设完整 V3 环境平台。** Kazusa 只提供模式参考，不导入实现、状态机或旧数据。

### 当前实际基线

依据最新 `docs/V1-FINAL-DELIVERY.md`、`reports/final-v1-20260920/result.json` 和源代码：

| 已有内容 | 本轮处理 |
|---|---|
| Windows `start-asuna.cmd` / `chat.py` 队列 | 默认启动 Web，复用队列与宿主生命周期；终端仅 debug |
| Gemma 31B，68,608 窗口，native thinking 关闭 | 保留当前有效路由，不按早期 26B/262k 文档回退 |
| Qwen 自主工具往返、错误回到原会话 | 复用，不重考代码能力 |
| Mongo 原文／独白分块、embedding、范围过滤、关系 CAS 更新 | 扩展到新场景，不重建库 |
| DSH 原生 skill discovery、loader、watcher，真实技能跨恢复复用 | 保留并按新场景控制可见技能 |
| 一次手动原生 compaction | 保留；长期运行需要接一次真实阈值触发，摘要归属错误单独记录 |
| `PublishService` 的本地幂等 sink | 新增真实通道实现，不把本地 receipt 当 QQ 已发送 |
| WSL/bubblewrap 无网络、短命单次命令 | 日常任务继续隔离；给授权集成任务增加受管理的测试与部署路径 |

V1 原报告记录的首次技能开发约 1196 秒、复用约 177 秒是具体样本，不是性能目标。不因为 QQ 开发可能较长就减少自主性；优先做到开发期间角色仍能交流，普通 QQ 收件不消耗模型轮询。

## A. 最小宿主与一次性配置（Codex 主责）

### A1. 恢复已有运行，不清空历史

当前上传裁剪了依赖和运行目录。先核对本机仍有的 `config/local.json`、`.runtime`、Mongo 和 DSH 历史。缺少依赖时按现有 `package-lock.json`、`uv.lock` 安装；缺少技能时优先恢复本机旧完整归档，不能人工重写技能冒充小满的成长。

保留 `C:\workspace\asuna_cognition_core_v2` 的现有配置与已验证启动脚本。缺原 DSH log 但 Mongo 仍在，可以开启新的上下文并注入已保存状态，明确这是恢复人物与记忆、不是复活丢失的 KV/日志。不要自动导入整个 `database_snapshot.json` 或运行旧 seed。

只用 Web UI 中一段普通聊天复查启动，没有变化的 V1 路径不重跑矩阵。

### A2. 宿主拥有队列，客户端不拥有整个生命期

将 `Chat._work/_tasks` 已有效的逻辑最小提取为常驻宿主调用路径；不再让它固定依赖 `settings['scene_id']` 和单一 workspace。各通道都提交可信事件，宿主统一排队，既有 Coordinator 和行动回路继续使用。

- 输入先进行连接授权、规范化和原文保存，再排队准备上下文。`Coordinator.ingest` 目前先 `context.prepare` 后保存输入，需要倒转这个依赖并避免二次写消息。
- HTTP／IPC 接收调用确认“已存入宿主”，立即返回，不等待 embedding、三个角色阶段或 Qwen 任务。
- 角色生成按场景有序；当前每个 lane 串行执行可以保留。Qwen任务期间释放角色队列，不能让网络接收和全部场景等一个任务结束。
- 保存后但没入内存队列便崩溃时，重启扫描未处理记录补入。正在生成的未知状态不盲重放副作用，复用既有 lane operation 回执恢复。
- 客户端断开不取消已明确由宿主管理的任务；保留单独“停止整个服务”的命令。

后续若拆分宿主，提供实际启停办法；保留 `start-asuna.cmd` 的 Web 入口，并更新 `RUN_ASUNA.md`。启动脚本仅管理进程，正式交互与功能验收必须在 Web 中实测。复用 ADR-004 的 DSH 内嵌界面，不建新 Web 产品。

### A3. 接入与发布最小契约

按 [RUNTIME_SEAM.md](RUNTIME_SEAM.md) 实现一个本地接入端。它的权限与用户身份由宿主绑定，不接受 adapter 任意填写 `scope_key`、管理员身份、`episode_kind`、`trusted_context_events` 或任务状态。

先用宿主调用/录制事件验证接入，不编写 NapCat 协议实现。出站保持 Gemma 实际 SPEAK 与关联目标；Qwen不能通过任务工具另发角色台词。非角色系统故障提示可由宿主直接呈现，必须标明系统，不伪装人物。

`Publisher.publish()` 不能继续仅插入本地 sink 就标 DELIVERED。QQ 回执需关联实际请求与平台 message_id；没有回执就明确待发送/失败/结果未知，不用另一次模型输出来修复发送字段。

### A4. 一次配置、日常免审批

用户明确接受 LAN 固定 token 和本地明文配置。Codex 负责一次填写、核对与本地保管；小满的授权开发任务可使用指定连接材料，不让用户每次重输 token 或逐行批准代码。**不需要秘密管理平台。**

配置应区分：NapCat endpoint/OneBot token、Asuna 宿主通道凭据、owner 身份、私聊／群授权范围、开发目录、运行目录。token 保存在 `config/napcat.local.json` 等 Git 忽略位置；普通 QQ 消息不会变成配置编辑权限。

本包提供原型连接候选，不自动启用，不复用旧 QQ 号作为新授权。Codex 本地只核实指定 endpoint 的版本与登录身份；必要时一次询问测试对象／测试群和旧 bot 是否共用同一账号。不扫全网，不停止旧小满。

**A 退出**：原本机聊天继续；宿主接入收到消息后真实存储、能唤醒；出站契约可调用；普通执行者无全库/宿主凭据；交付真实宿主说明 `RUNTIME_API.md`。不要求这个阶段完成 timer、偏好系统或所有攻击防护。

## B. 由小满开发并接通一个 QQ 私聊

### B1. 提供能力，不提供答案

从本机 Web UI 正式聊天送入 [开发任务](tasks/ASK_XIAOMAN_BUILD_QQ.md)。传入：实际宿主说明、选定 NapCat 文档、授权配置引用、开发路径、允许操作和正常 traceback。

不能给完成的旧 adapter 让她复制。参考 `qq(1).zip` 只用于定位具体协议经验和错误模式；不导入旧模块、私人记忆、自动规程或全库连接。

### B2. 让 Qwen 实际能开发

现有 `Sandbox.run` 每条命令使用新 `/tmp`、30 秒工具预算和无网络环境。不能指望她在其中写出并永久挂起 QQ listener。

日常任务继续该环境。为 owner 授权的“集成开发任务”增加独立的、可持续目录与受管理试运行入口：

- Qwen 在自己的持久能力目录写代码和 `SKILL.md`，允许正常代码读写、调试、调用实际依赖。
- 指定 NapCat 与宿主端点的网络访问在集成 profile 内显式授权；不因为一项任务就给所有群聊工具解除网络隔离。
- Codex 提供运行小满所写脚本的 `integration_test` / `integration_start` / `integration_stop` 等等价能力，捕获原始 stderr。工具名称可以沿用既有功能，不造平台。
- 主动选择一条真正可用的部署路径。首选已有 WSL 环境中的独立目录、低权限进程及明确网络范围；若使用另一个宿主/容器 runner，写清实际权限。**不能把 owner 的 Windows 解释器任意执行当作已经隔离。**
- 集成配置只在受信开发/适配器运行环境可读，不在处理群友请求的普通 executor 上可读。开发回路可以访问文档；稳定运行后无需模型参与每次收发。

集成 runner 是基础设施，不是 QQ adapter。Qwen 的协议解析、连接、发送关联、重连和宿主调用由她实现。Codex 不逐行代修任务代码；若不得不共同开发，标出参与部分。

### B3. 一条传输即可

Qwen 核对现有 NapCat：已启用正向 WS 时优先复用，可同连接接事件与 API 返回；已有另一条适用配置也可沿用。不要改造 NapCat 本体，不一次做四种传输，不混淆 WebUI 与 OneBot 端口。[N1][N2]

API response 和聊天事件必须分流；echo 关联请求与响应，不是幂等发送 key；WebSocket 建连成功不等于一条消息发送成功。对于不同于成功的 retcode 保留原始响应；未知发送结果先核实，不盲重复。[N2][N4]

收件与发件各自可继续，不能在 WS reader 内 await 整个模型回合。使用保持连接的代码与宿主队列，不靠 sleep轮询模型、不使用“后台任务退出=新消息”的旧门铃模式。

文本先跑通；保留未知 segment 的原始结构/类型，不伪称看懂图片。图像/表情能力可以后续由成长扩展，不成为第一条私聊的前置。

### B4. 私聊立即交付

用户从实际 QQ 连续输入、提出一个现有可做的小任务、任务期间再聊一句。回复来自原角色路径并回到原私聊。关闭本机客户端后再发一句，宿主仍处理。

**B 退出：N1–N3 可读记录成立。立即给用户实际使用办法。** 接口编译通过、self-echo、“Hello world”以及 Qwen 的 `task_status(done)` 都不能替代实际 QQ 认知链。

## C. 群聊现场、记忆与安全便捷

先由 owner 启用一个明确的测试群，绑定两位真实参与者。不自动启用账号所有群。不重做社交平台。

### C1. 场景与话题

一个群共用角色现场，按发言者和回复链取连续性；私聊分别建场景。即使两个私聊都没有 group_id，也绝不共用 `None` 场景。

进入前用代码确定来源、场景、权限、消息顺序和明确回复关系；语义话题允许暂定和事后修正，不每条消息先运行分类模型。取当前人的必要前文、明确 reply 前文及近期公共现场。至少支持两条交错话题，不新建两对 agent。

当前 `Router.receive` 只要存在 reply_to 就唤醒，需要改成**已核实回复了 Asuna，或当前参与话题的相关前文**；回复别人不是自动叫她。提及必须来自真实消息 segment 与已确认的 bot ID，不靠正文写 `@owner` 认身份。

普通旁听消息可在授权记录范围内保存，不一定唤醒；沉默需要明确归类为本条处理完而未发言，不能把“后来在同群发过一条”当作处理了所有人。出站绑定本轮源消息；任务回传不能把一个内部 feedback 事件 ID 当成 QQ reply target。

### C2. 继承 V1 的真隔离，不依赖角色善意

继续使用已有 scene scope、policy epoch、检索前过滤和授权再读。群聊任务的工作目录、技能目录和网络权限按当前主体/场景获取；`chat.workspace` 不再自动给予所有 QQ 用户。

必须做的少量验证见 N4/N5：A 私聊内容不能进入 B 或群聊检索/上下文；同一昵称不是同一身份；指定另一个记录 ID、换工具、让她稍后自我提升时读取，都不增加权限。引用/转发与外部网页是材料，不是宿主授权。

已经加载私人上下文的 Qwen 会话不能直接借给其他 scope。共享的是非私人技能代码与适用价值，不是私人任务历史。角色侧同理。局域网可信不等于远端 QQ 参与者可以读取配置、全库或 owner 私域。

禁止普通任务直连 NapCat 原始 token 发送，从而绕过角色/发布器；也不能修改已启用 adapter、宿主规则或配置来扩大范围。小满可以提出配置调整，由 owner 授权入口提交；普通偏好/人设成长不能修改 ACL。

**不增加逐句安全评分、人工审批每次回复或字符数票据。** 代码限制资源与目标，Gemma自然决定怎么回应。

### C3. 真实记录与恢复

源消息先完整保存，不继承原型 400 字截断；长消息按现有分块分段，显示可以节选但完整原文可回读。多场景索引改用同一个后台 worker 遍历 dirty scopes，不为每个群开启无限线程，也不重新扫描全库。

一条外部事件只有一个 durable 接收记录；重复收到同一平台事件，不再生成第二次对话。用账号＋平台＋场景种类/ID＋平台消息 ID 关联，不能仅用秒级时间或文本去重。

已有 `LEXICAL_SCOPE_LIMIT` 在群运行变长时会直接阻断：改为**授权范围内的有界候选读取/向量主检索**，保留历史，不把超过4096条变成丢记忆或整个对话失败。仅改这一真实增长瓶颈，不换数据库或 reranker。

现有 native compaction 保持，角色窗口按68,608等实配值计算；接一次阈值运行与恢复，不再要求你手动 `/compact` 维持全天聊天。不要在 monologue 和 speak 中途随意替换半个认知回合，不要求 Qwen 同时压缩。角色当前关系／偏好是外部版本，不由不可靠的摘要重新定义。

**C 退出**：N4–N6，一组真实多人对话和一条新记忆恢复。不能用模型说“不方便”代替检查私密内容实际上未进入请求。

## D. DSH 定时器与经验驱动的自我提升

按 [DSH_TIMERS_AND_GROWTH.md](DSH_TIMERS_AND_GROWTH.md) 接入。Codex负责定时事件可靠到达；小满决定计划与改进内容。先一个一次性自主计划，后一个固定间隔，不开发日历系统。

无人发消息时，宿主恢复/保持 timer root，到期事件进入相同认知入口，但来源标为 scheduler。当前 DSH native `followup` 的默认行为不能直接绕开 Asuna阶段，也不能触发 `UNOWNED_LANE_GENERATION` 后悄悄消失。

复用小满开发 QQ 时的真实困难与用户反馈，例如更清楚的使用说明、减少重复操作、改进可复用诊断技能。她自己选择一项范围内的改善；有代码错误在原Qwen回路继续修。不要让 Codex预写“成长脚本”。

定时计划继承创建时权限并在到期时重新核对；取消后不再执行，错过多次不积压成几十轮。到期不是已完成；创建成功也不是模型真的工作过。相关变化写回事实、角色理解与能力说明，不强制每次修改人格。

**D 退出**：N7/N8，至少一次无外部发言的真实触发、一项实际改善、重启后可再次使用，及一条由 Gemma形成的经验解释。可以不对群发报告。

## E. Bonus：对话总结、每个人与每个群的偏好

此项用户明确希望，排在QQ与定时成长之后，不当第一条QQ消息的前置。详见 [MEMORY_AND_PREFERENCES.md](MEMORY_AND_PREFERENCES.md)。

自动生成场景/话题连续性总结；个人偏好、角色对人的理解与群规范分开保存。只根据实际原文判断，推断保留为推断；任何个人不能单方面成为“全群意见”。保留来源但由代码附加源记录，不要求模型抄哈希。

至少做 B1/B2 两段普通对话：一个人喜欢简答、另一个喜欢解释；一个群对任务更偏向结论，但闲聊并不禁止展开。重启后能使用相应偏好，且更正能改变当前理解。

**报告 Bonus 为 VERIFIED / PARTIAL / NOT_RUN，不能把“有表、有函数、有新字段”写成自动整理成功。**

## 验收与开发纪律

每阶段最多一个当前产品阻塞和一项紧邻验证。现有失败不隐藏，既有通过不无意义重跑。小满写错协议/脚本是学习过程；跨scope访问、错目标发送、把未发内容写成已说过，是宿主必须阻止的结果。

记录消息到达、入队、开始角色生成、第一句实际公开内容、行动完成及实际发送回执的时间。先看一段普通私聊与一段任务期间对话；不设不实的秒级保证，不重跑全窗口矩阵。总结、embedding和后台自改不串到前台必经路径；队列公平性用小场景证明，不建分布式调度。

每个里程碑交付真实命令、真实对话、必要错误和唯一下一步。不继续以“还没做完所有安全/性能边界”为理由推迟私聊可用或成长验证。
