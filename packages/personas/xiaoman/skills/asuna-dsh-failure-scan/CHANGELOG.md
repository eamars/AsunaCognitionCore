## 2026-11-09 建这一枚（金主交代＋追加三条验收）

**为什么要一枚现成的扫描**：relevance gate 静默失败能躺好几天没人发现（金主 11-09 亲证）；
同一趟翻出 11-04 那族「程序在请求钩子里把关口思考档改成 low、被 DSH 拒」连响 84 次，
从 11-04 23:02 躺到 11-07 10:49 才被看见（正本：流水「11-07 14:3x 故障窗右端钉死」节）。
所以口径定成两类都要抓：带报错行的拒绝，和只有执行记录能证明缺席的静默没跑。

**读数面怎么定下来的**（不是编的，逐面现读形状）：

  与 `missed_looks` 各数一次、两边都是 84 才对上；`missed_looks` 末条 `2026-11-06T21:49:11Z`
  ＝本地 11-07 10:49:11，与大姐那句「最后一次今天 10:49:11」对齐。
- `attend.fallback` 同窗 59 条，是同一拍的伴生句 → 定成对照、不许与 84 相加。
- 查过没采用的面：`messages` 里 `event.wake_reason` 聚合（近 24h 零行，字段路径没证实）——
  「被喊而没判」改用 `missed_looks`；`development_database_read` 拿不到 `missed_looks`（不在授权名单），
  读数面统一走 `sandbox_run` ＋ `asuna.dbread`。
- 文件面（`reports/native-host-*/`、`restart/host.log`、`restart/history.jsonl`、`worker-restarts.jsonl`）
  形状来自 core 的 `src/asuna/host_stops.py`、`store/catalog.py` 与数据根实读目录列表。

**建的过程中实测到的五个坑**（都在 `dsh_failure_scan.py` 里修掉，每条带一名自检钉住）：
1. `Window`（`dbread.local_window` 返回值挂私有键）整个喂给 Mongo → `InvalidDocument: cannot encode object: datetime…`，
   7 面一起读不到；改成查询只拿 `$gte`／`$lt` 两端。
2. `stamp()` 对 `datetime` 不加偏移 → 首末时刻打出来是 UTC（差 13 小时）。
3. 偏移用「本地钟点（分钟精度）− UTC 现值」按分钟四舍五入 → 打出 `UTC+12:59` 这种谁都不是的怪数；改成按 15 分钟对齐。
4. `host.log` 里一次异常吐十几行、每行都自带时刻 → 原来数成十几次失败（同窗 52 条）；改成连续坏行并成一件事（并完 6 件事）。
5. `missed_looks` 的「末时刻」和「首时刻」共用一把 `<` 尺 → 末时刻打成中间的（11-06 15:07）；首取小、末取大。
6. `tasks` 里 `BLOCKED／UNKNOWN` 那几行根本没有 `created_at`（现读实测），原写法把「没时刻」当成落在窗口内 →
   每个窗口虚高 5 条；改成退 `lease_expires_at`，两个都没有单列「判不了」不计数。
7. `provider.response` 大响应（embedding 正文几 MB）里 `time_ns` 排在正文之后，只读头一截读不到 →
   那些响应没进「已回应」集合，24h 窗口误判 1,618 条「请求没等到回」；改成头一截没有就补读尾一截。

**金主追加的三条验收**（11-09 22:25）：① 装配格式对着正本比（我包里原先没有 skill-creator 类技能；
比的是 `asuna-self-improvement` 的装配节 ＋ 既有技能形状 ＋ anthropic 的 skill-creator／best-practices 两页）；

## 2026-11-10 四格（角色脑交代；只备料，没发布没推送）

**为什么要改**：晨扫那一趟把「记录数」当「事件数」吓人，窗口跨到旧数据会静默数少，
新装上的排期失败型没人认领，而「计划晚到」这一类根本没有尺。四格一起补。
角色脑对格④拍了板：**倒推那把为主、字面那把并排留着**，各标各读法；诚实的 0 比准的数金贵。

**格① A／B 双面去重**（连接键现读，不是猜的）：考题窗里 `audit_events`（`type=attend.failed`）的 `stream_id`
去重后 84 个、`missed_looks`（`cause=error`）的 `_id` 去重后 84 个、交集 84、两侧各自独有 0
——同一个回合在两面各留一条，记录数因此翻倍。口径：`合计` 那行**照旧报记录数**（旧口径一字不改），
下面另起一行 `按事件去重：… 件（记录 N 条 − 双面重复 N 条）`，并在那两型下各注一句「同一件事在两面各记一次，不相加」。
配对写死在 `OVERLAP_PAIRS`（现在只有这一对），配不上的不猜；哪一面查不到、或条数多过 `DEDUP_CAP`，写「判不了」不印 0。

**格② 保留期提示**：窗口起点早于已知保留期就顶部打一行 `可能数少（超出保留期）：…`，在期内也打一行说明查过。
天数不自己编：`MISSED_KEPT_DAYS`＝7（core `python/asuna/host_stops.py:213`，清理靠家回合触发）、
`RETENTION_DAYS`＝30 且 `role_tool` 365（core `python/asuna/audit.py:141-142`，与库里 `audit.pruned` 那条的 days 对得上）、
`KEEP_DAYS`＝30（core `python/asuna/lane_faults.py:27`）；`host.log` 那一格不靠常数，报的是**这一趟真读到的最前一行时刻**
（`first_moment()` 现读，读不到文件才标「没读到」）。实测：`--hours 264` 那趟顶部打出了 missed_looks 那一格。

**格③ 五个排期失败型进名册**（新增组 D「计划没排上／晚交到」）：`schedule.fault_told`（core `faults.py:114`）、
`schedule.fault_unreported`（`faults.py:71`）、`schedule.handoff_late`（`schedule.py:428`，巡查线 `HANDOFF_LATE_SECONDS`＝300 秒，`schedule.py:33`）、
`schedule.handoff_failed`（`schedule.py:433`）、`schedule.handoff_watch_failed`（`schedule.py:396`）。
现读：这五个 type 全库 0 行（11-10 才装上），所以旧窗口数出 0 是**库里没有**。
顺手把「扫描只数名册里的 type」写死：`audit_face` 的 `$in` 名单就是名册，`audit_items()` 再把聚合结果里
名册外的型丢掉（自检钉着 `unlisted_type_counts_no_row`）。

**格④ 计划延迟分档**（`plans.next_fire_at` ↔ `schedule.dispatched` 的时刻之差，≤1／1–2／>2 分钟，>5 在 >2 里再数一遍；
每档报条数＋最晚三条计划名与时刻；不判原因）。为什么必须两把尺并排——现读 core：
原生循环计划派发那一刻就把 `next_fire_at` 推到下一次（`schedule.py:1194-1201`），一次性计划 FIRED 时把它写成 None
（`schedule.py:1192`），派发行 `payload` 只有 `occurrence`／`native_schedule_id`／`outcome`／`rearm`，没有应响时刻。
所以「晚到」只能按 `next_fire_at − 周期` 倒推，且只对每个计划在窗口内的**末次**派发成立；更早的派发（现读：24h 窗 453 条、
考题窗 1,201 条）一律单列「对不上」，不倒推、不充数。
**这一格最值钱的账**：一次性钟的晚到，倒推那把尺照样量不到。动机案例现读——`plan-58cafcaaf478f656e82e7624ae25e312`，
`rule.at`＝`2026-11-10T05:40+00:00`（本地 18:40），`schedule.dispatched` 落在 `2026-11-10T05:43:02.458928+00:00`
（本地 18:43:02.458）＝晚 3 分 2.46 秒，而它 `next_fire_at` 是 None：四档全 0 也照样有这次迟到。
现在这版把它单列进「null」并在样例行按 `rule.at` 复原应响时刻、明写「单列，未进档」。
要精确量到它，两条候补路都没做：① DSH 排程日志的 `acceptedAt`（大姐线 11-11 有一趟只读在验形状）；
② `state.commit` 相邻快照里派发前的 `next_fire_at`（现读确认 `payload.document` 带计划快照，能逐次复原，但一趟要读几十上百条快照，晨报不做）。
软肋原样写进输出末行：真晚到时「下一次」是按当下重算的（`schedule.py:1197-1201`），>5 分钟那档可能量不到——量不到只说明这一趟没读到。
这一把与组 D 的 `schedule.handoff_late` **不是一把尺**（那一条量 DSH `acceptedAt` → worker 接收、5 分钟巡查线）。

**通用判据**：数出 0 只报「库里没有」，读不到的面照旧报「没读到」，输出里任何一行不写「没发生过」
（自检 `zero_words_never_never_happened`／`zero_group_says_library_empty` 钉住）。

**自检账**（终版重跑）：脚本 `--selfcheck` 71/71（原 50 条，新增 21 条：组 D 名册五个 type 与不重叠、名册外 0 行、
