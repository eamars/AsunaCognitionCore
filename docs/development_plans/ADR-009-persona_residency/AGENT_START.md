# ADR-009 实施入口（给实施 agent）

你要实施的是 ADR-009。这个文件夹自成一体：**不需要其他仓库，也不需要任何聊天记录**。本文件是唯一入口，其他文件在需要时查阅。

## 决定（一段话）

核心只提供与人格无关的类人能力原语：情感账本、人物档案、文档层、记忆显著度、节律、心跳、夜间沉淀、人格数据 API 与人格作业。所有状态以 Mongo 修订账为唯一真相，文件只承载行为。人格（当前安装的是小满）是可替换的插件，**她用这些原语自己完成入住和以后的成长**。同时收完 ADR-008 剩余的 DSH 对齐，并清理遗留代码。完整背景见 [README.md](README.md)。

## 先做什么

1. **只读确认现场**：`git status`、`git log -1`（基线应为 `8b5a94a1` 或其后代）、`package.json` 中的 DSH 版本。本机若有未提交改动，不覆盖、不 reset。
2. `npm ci` 后，在依赖树中逐项复核 [DSH_ALIGNMENT.md §2](DSH_ALIGNMENT.md#2-已核实的-dsh-02-事实) 的事实；有任何不符就停下（见下文"停下来问的条件"）。
3. 跑一遍现有测试，记录基线结果：哪些通过、哪些因环境原因跳过。
4. 按 **P0 → P7** 顺序实施（[IMPLEMENTATION.md](IMPLEMENTATION.md)）。每个阶段单独交付，阶段内可以分多个提交。

## 必须遵守

| 规则 | 说明 |
|---|---|
| **人格中立** | 核心代码、核心 prompt、核心工具、示例配置里不得出现任何人格名、人格正文或人格专属参数。测试用合成人格 `demo` |
| **不替人格做她的事** | 不写她的迁移清单、解析器、召回题库；不标注她文档的可见性；不选她的参数值；不导入她的真实数据；不修改她的人格正文 |
| **个人数据不进仓库** | 示例与夹具只用占位符（`192.0.2.x`、`example.invalid`、`demo-*`）。真实账号、地址、主机名、用户名、时区、私密内容一律不写进跟踪文件，包括提交信息与阶段报告。提交前运行 `tools/check_staged_secrets.py --personal`（P0 之后可用） |
| **隐私谓词** | 每新增一个读路径，都要过 [ARCHITECTURE.md §2](ARCHITECTURE.md#2-隐私与可见性模型) 的判定，并配一条泄漏测试 |
| **失败语义** | 新的 DECIDE 可选字段，单项失败只记入 `rejections`，不打断回合；整体 JSON 解析失败仍按原规则处理 |
| **不静默截断** | 预算超限时拒绝提交或抛错，不返回截短的结果 |
| **沿调用链删除** | 见 [CLEANUP.md §1](CLEANUP.md#1-原则) |
| **Web 是唯一交互面** | 沿 `AGENTS.md`：交互和人工检查走 Web UI，不用终端聊天或 stdin 注入。人工检查只在**演示环境**进行（[IMPLEMENTATION.md §0.3](IMPLEMENTATION.md#03-demo-演示环境人工检查与本地冒烟)） |
| **人格包里的个人标识** | 人格包的代码和文档（skills、集成、自检脚本）中出现的 owner 个人标识，**可以并且应当**替换为占位；这不算修改人格。人格正文（人格、口吻、价值观文本）仍然不碰 |
| **职责名不是模型名** | 角色脑、行动脑、评估路由各自独立配置，UI、兼容逻辑和计数不得从路由名推断模型 |

## 不要做

- 不建 marketplace、通用插件管理器、workflow 设计器、第二个数据库、向量库、md 同步守护进程。
- 不替换 `SceneQueue`、`ToolBroker` 文件工具、委托显示（[DSH_ALIGNMENT.md D-10](DSH_ALIGNMENT.md#d-10-明确不采用本-adr-内)）。
- 不改模型服务部署，不升级 DSH，不修改 `node_modules`。
- 不重写 git 历史。
- 不把 `docs/development_plans/**`（本文件夹除外）当作现行行为的依据，也不修改它们。

## 停下来问的条件

遇到以下任何情况，停止当前阶段，在报告中写清**确切现象、可选方案和你的建议**，等 owner 回复：

1. DSH 的接口名、签名或行为与 [DSH_ALIGNMENT.md §2](DSH_ALIGNMENT.md#2-已核实的-dsh-02-事实) 不符，且没有等价的公开接口。
2. 实施需要改变 ADR-007 或 ADR-008 已裁定的语义（单库、forward-only、自开发地板、原生会话归属）。
3. 某一步需要人格本人的决定，例如可见性标注、参数取值、清单内容、题库内容。
4. 需要读取或写入真实人格数据，或者需要真实 QQ 发送。
5. 条件删除的检查结果不满足条件（例如存在未迁移的旧计划行）。
6. 现有测试中，有你判断为"不变量"的测试必须删除才能通过。
7. 发现本 ADR 自相矛盾，或与代码现实冲突、无法同时满足。

## 汇报格式

每个阶段结束时提交一份报告（写在 PR 描述或阶段提交说明中；不得包含个人数据）：

```text
阶段：Pn
提交：<hash 列表>
完成：逐条列出 IMPLEMENTATION.md 中本阶段测试编号 → PASS / FAIL / SKIP(原因)
反证：哪条测试在基线上失败、改动后通过
删除：文件/符号 → 为什么无人调用 → 用什么验证（grep 命令）
偏离：与本 ADR 不同的实现及理由（无则写"无"）
未验证：需要真实模型、浏览器或硬件才能验证的项
人工检查：ACCEPTANCE.md §4 本阶段条目的结果（截图在本地 reports/，不入库）
下一步：下一阶段的第一步
```

## 完成标准

- P0–P7 的全部测试通过，或按停止条件在报告中说明为何无法通过。
- [ACCEPTANCE.md](ACCEPTANCE.md) 的矩阵逐项有证据。
- 当前手册（`README.md`、`RUN_ASUNA.md`、`RUNTIME_API.md`、`NATIVE_PLUGIN.md`）写的是**现在怎么用**。
- 最终报告提醒 owner 两件只有 owner 能决定的事：
  1. 公开前是否清理 git 历史和历史设计文档中的个人标识；
  2. 人格满意后，是否把源根切换为 `cutover`。
