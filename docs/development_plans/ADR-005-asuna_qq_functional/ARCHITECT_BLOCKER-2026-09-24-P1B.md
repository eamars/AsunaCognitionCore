# ADR-005 P1-b：历史查询无法接入现有宿主的授权边界

2026-09-24 11:30（Pacific/Auckland）｜供架构师裁定｜当前状态：阻塞端到端交付，草稿修错仍可继续

## 需要裁定的事

请明确一条**受控的宿主接入与验收路径**：由谁、在什么授权范围内，把小满在独立开发环境写出的历史查询代码接入现有 Asuna 宿主，并在隔离数据上运行同一实现，随后按现有 Web/QQ 入口启用和验收。需要具体界定可改的宿主模块、测试数据访问方式、部署/重启操作者。这里不请求新增面向 QQ 群友的权限，也不预设新增公开 HTTP 接口或第二套运行时。

## 用户可见的失败

9 月 24 日 11:08，用户在现有 Web 问：“我之前在本机聊天里亲口说过关于‘雾灯’的什么？请找出包含‘雾灯’的完整原话、时间和出处。”小满 11:09 的回复把**自己**说过的两条话当成用户原话，并称没有精确时间。那一轮之前，宿主保存的同场景消息中，用户确有四条含“雾灯”的入站原话，均带时间。现有角色上下文只选到两条相关的角色公开发言和有限记忆候选；它没有完整原始消息的按词/人物/时间查询能力。因此这是当前实际功能失败，而不是单纯的显示问题。

## 当前系统为何不能由小满独立完成接入

- 完整原始聊天保存在**现有 Asuna 宿主的 Mongo `messages`**；角色当前只收到有限近期历史和检索候选。ADR-005 已裁定应在这个宿主中按授权场景查询原始消息，并通过现有角色/行动路径回读来源。
- 小满的行动脑目前通过受管理的 `integration_dev` 在**独立持久目录 `/task`** 写代码；测试时该目录被复制为只读 `/app`。这不是正在运行的宿主源码目录。她写出的 `host_wiring/history_query.py` 仍是草稿，运行中的 `src/asuna` 没有该模块，也没有把查询能力交给角色/工具路径。
- 该受管理环境可达的是**频道适配接口**：它接受经认证的入站事件、提供会领取待发消息的 outbox，以及发送回执；没有历史查询入口。本轮对若干历史查询 URL 的只读 GET 探查均得到 400；也没有 Mongo 转发。尤其不能把 outbox 的 GET 当作只读历史查询，它会领取待发送项。行动脑不能从这里运行针对真实宿主 `messages` 的查询，也不能借入站接口安装宿主代码。现有 Web 能给操作者显示消息，不等于行动脑获得了历史查询工具。
- 9 月 24 日早些时候，Codex 曾获**一次性**授权接入 P1-a 的 QQ 身份快照并重启宿主；该授权明确不覆盖 P1-b。把 P1-b 草稿留在独立目录或只跑其假存储测试，都不能使 Web/QQ 用户用到历史查询。
- 宿主现有身份模块已经承载 P1-a 的真实 QQ 对话接线和一次措辞修正。独立目录还有一份同名身份草稿，二者不是可直接互相覆盖的版本；部署 P1-b 时必须按**当前运行宿主接口**核对导入与兼容，保留已工作的 P1-a 行为。

草稿曾有无时间窗条件、人物过滤分页顺序和身份模块导入问题，后续已在独立目录修正；12:17 的真实 Mongo 只读探针仍找到一个已送达出站时间回退缺陷，正交给小满修。这些是普通实现问题，**不是这里请求架构裁定的原因**。本问题只针对修好后如何在既有授权边界内接入和验证。

## 裁定需给出的最小边界

1. 宿主代码由小满在何种受控路径提交，以及谁有权把它写入运行宿主并执行必要重启；若继续沿用独立草稿加人工接线，也请明确接线者和授权范围。
2. 如何让实现者在**隔离宿主与隔离数据库**中检验真实 `messages` 结构、授权过滤和分页，而不向普通群聊开放数据库凭据或生产数据接口。
3. 接通后如何在现有 Web 自然提问中核对完整原话、实际发言者、时间、场景与来源，并区分字面穷举与向量候选。9 月 24 日的失败样本可作为复测材料；无需为验收新增另一套交互入口。

在裁定前，已授权的草稿修错和离线检查可继续；**P1-b 不能标为运行可用**。本文件记录待决授权/接入边界，不替架构师选择新的系统结构，也不授权修改生产权限。

## 12:05 补记：导入缺口已与接入阻碍分开

小满在独立目录修正了查询草稿的私有 helper 导入，离线检查报告 95 pass / 0 fail。Codex 随后用**当前宿主实际的身份模块**与该草稿进行只读组合导入，结果为 `import=OK`、当前宿主不含那两个私有 helper、`identity_complete=True`、`identity_source=peer_context`。这证明导入缺口已不再是阻止接入的理由，也证明**不需要覆盖现有 P1-a 身份模块**才能取得身份解析；小满旧版接线说明中的覆盖建议已要求更正。上述检查没有运行真实 Mongo 查询，也没有把模块装进宿主。真正待裁定的仍是前述宿主写入、隔离数据验收和部署责任。

## 12:17 补记：只读真库探针缩小了技术不确定性

Codex 在宿主侧只读加载当前查询草稿，针对生产 `messages` 的本机 `local-dm` 历史，以“雾灯”、用户 `local-user`、明确时间窗做字面查询，返回了提问前四条用户原话（场景序列 84、82、80、46）。每页一条续查四页，无重漏。这说明草稿的这条入站查询链已经通过真实 Mongo 数据验证；不代表角色能通过 Web 使用它。

同一查询去掉人物过滤时，草稿遗漏两条已经送达的本机 Web 角色公开回复（场景序列 81、83）。原因是这两条 `messages` 记录有 `direction=outbound`、`phase=SPEAK`、`delivery_state=DELIVERED` 和 `receipt` 引用，但没有 `receipt_at`；时间实际在现有 `sink_receipts.received_at`。这是交给小满修的**普通查询实现缺陷**，无需架构师为它新增存储或接口。查询草稿修好后仍不能自动进入宿主的角色/工具路径；本文件的待裁定接入责任不变。

## 12:36 补记：执行侧连续输出截断，草稿修复无法落盘

小满已明确认领上述普通缺陷，但同一修复目标连续四个行动回合因模型输出达到上限而中断；其中后一个回合在**还没有执行任何工具步骤**时就截断了。第一回合曾完成身份导入简化，此后 `sink_receipts` 时间回退始终没有写入草稿，故不能把自动重试当成进度。

这不是 DSH 压缩阈值遗漏。Asuna 源码和正在使用的 executor DSH 配置快照均确认：压缩引擎 `thresholdRatio=0.8`、运行桥 `pressureThresholdRatio=0.8`；行动模型声明 `context_window=262144`、单次输出上限 `max_tokens=8192`、`reasoning_effort=high`。四次失败的最后一次真实服务回执分别为输入 69113、38372、80636、40191 tokens，输出均为 8191 tokens，服务 `finish_reason=length`，DSH 记为 `max-tokens`。输入远低于约 209715 tokens 的上下文压缩触发线；压缩历史不会解决**一次生成耗尽输出配额**。Codex 已通过 Web 请小满把下一行动缩为一次文件修改，测试另起一步；仍需看实际落盘结果。

当时尚未核对另一台 DSH 的同模型配置；下面的补记已确认 8192 是本机可修正的配置差异。**输出配额不再请求架构师裁定**。本文件仍待裁定的只有前述宿主接入与验收授权边界。

## 13:00 补记：输出上限配置差异已定位并修正

Codex 按用户提供的线索，使用另一台 DSH（`192.168.2.10`）现有的只读 PRC 设置接口查询到：同一 `qwen38-next-uncensored-freetoken-vision` 所属 provider 的 `defaultMaxTokens=32768`，该模型没有更低的单独覆盖；实际模型服务启动参数为 `--max-output-tokens 65536`。因此 Asuna 本机的 `8192` 是配置限制，**不是模型最高输出**。原先四次 `8191`/`length` 与这一本地限制吻合。`0.8` 压缩阈值的核对结论仍成立，但不能用它解释 8192 的选择。

已把本机行动模型覆盖配置的输出上限改为 `32768`，重启宿主后，活动 executor DSH 配置快照中 `asuna-compaction` 与 `asuna-runtime` 均为 `maxTokens=32768`；Web 模型设置显示 `32768`。新一轮经 Web 授权入队的 P1-b 窄任务，真实 `provider.request` 已携带 `max_tokens=32768`，此前的连续输出截断原因得到配置层修复。该行动的文件修改和完成状态仍须按实际结果核验；**不能由请求参数推断 P1-b 已实现或端到端可用**。这项运维修正没有改变角色路由、宿主架构或小满的开发权限。

## 13:17 补记：独立草稿已有修复，宿主接入仍待裁定

小满在独立 `/task/host_wiring/history_query.py` 写入了从现有 `sink_receipts.received_at` 回退取本机 Web 已送达出站时间的实现。Codex 只读加载这份草稿，与当前宿主身份模块组合查询真实 Mongo：此前漏掉的场景序列 81、83 已找回，时间来源标为 `sink_receipts.received_at`；同一字面查询逐页读出 9 条，未见重漏。QQ 私聊与群聊已有的 `messages.receipt_at` 路径也能读到。**这些是独立草稿的只读验证，不是运行宿主已接线。**

普通实现审阅还发现该回退分支每次只扫描按场景序列降序的前 400 条候选。用 401 条隔离内存样本分页两页后，结果报告 `more=false`，最早一条未返回，虽附有 `truncated=true`。这一完整性问题应由小满在授权开发目录修正，不能作为架构新权限请求。本文首节所需裁定的宿主写入、隔离数据验收和部署责任仍未解决；P1-b 不能据当前草稿标为运行可用。
