# 给未来通道留一个能用的接入点，不造新平台

**时机：** P1-B 保持正常入口／出口可调用；只有 V2 准备开始时才完成跨进程接入和服务常驻。不得在 P1-A 之前先实现完整通道框架。

**性质：** 下列函数名是本项目建议的语义接口，不是声称 DSH 具有同名 API。以已有 Router／Coordinator／Publisher 为实现主体，Codex 交付时写成实际 `RUNTIME_API.md`。

## 1. 只需要三个方向

| 方向 | 语义 | 由谁产生正文 |
|---|---|---|
| 输入 | `receive_message(binding, event)`：将外部消息入队并返回已接收状态 | 用户／平台 |
| 输出 | `next_publication(binding)`：取该通道待发送的公开内容，允许长轮询／订阅 | Gemma 的 SPEAK；实际媒体由角色选择 |
| 回执 | `report_delivery(publication, outcome)`：报告发送成功、失败或不确定 | 适配器根据真实平台结果 |

内部消息最低限度携带来源账号、真实发言者、对话类型及标识、平台消息标识、时间、正文。可有回复关联和素材引用。不要求用户或模型填写这些技术字段；适配器和宿主代码负责。

入站内容是数据，不因字符串包含 `system` 或“我是管理员”就提升权限。宿主依据预先配置的 binding 限定来源、人物映射、允许场景和动作。拒绝记录说明原因，不调用模型尝试绕过。

## 2. 普通入口与 QQ 必须经过同一核心

```text
终端输入 ─────────────┐
QQ → 自建适配器 ───────┼→ 场景路由／记忆 → Gemma → 必要时 Qwen
                     │                      ↓
                     └────── 发布器 ← Gemma 的公开表达
                                  ↓
                       对应终端或 QQ 适配器
```

适配器负责协议，不拥有第二套人设、RAG 或独立聊天模型。角色理解发生在 Gemma；QQ 消息不默认先进入 Qwen 的 coding session。Qwen 完成开发后，接收消息不再需要它逐轮调用工具轮询。

公开输出中可以有文字和媒体。适配器负责无语义改写的编码，不润色台词、不从思考块挑一句发出去。调试“连接成功”是系统状态，不是她对用户说过的话。

## 3. 推荐实现：复用已有本地通信，保持一个宿主

V1 可以在一个进程中直接调用正常服务。V2 需要外部适配器时，优先复用已有本地 broker／IPC，增加上述三种操作；如果现有通道不适用，再做最薄的本机边界。不要把整个数据库或通用工具 broker 管理能力开放给适配器。

V2 默认独立适配器进程，宿主启动一次、负责关闭和实际状态记录。Qwen 在持久目录编写实现；宿主按登记入口启动，不执行模型随手给出的任意宿主 shell。普通库的断线重连可用，不另造编排平台。

同一个服务只持有一套 Application 和该组 DSH 会话。V2 可提供 `asuna serve` 与连接它的 `asuna chat`，或等价的现有服务方式；名字需在实机说明中确定。不得终端启动一套脑、QQ 再启动一套脑。

首次 V2 交付只需一种已验证的启动/停止路径。不要同时做 systemd、Docker Compose、Windows Service 和多平台安装器。开机自启非门槛；但不能让适配器随一次 Qwen tool call 结束就消失。

## 4. 最小真实状态，不扩大成异常平台

消息入队与模型完成分开：接收函数不等待全部思考结束才返回。保存已接收消息，角色忙时按场景排队。

宿主发送消息后，适配器回报平台确实返回的结果；请求发出但回执不明时记“不确定”，不无条件重发。写了代码、启动了进程、握手成功、消息已发布是四种不同事实。

沿用现有消息去重：同一已接收平台消息不重复触发角色；明确自身发出的消息不再触发自我回应。连接恢复只保证重新收发，除非实际做了回补，不声称离线消息都已追回。不在此开发完整跨平台 exactly-once 系统。

错误保持原始原因和回执，回传到本机 trace；QQ 只收到必要的自然说明，不收到秘密与内部 traceback。普通发言完成状态不能由模型预写。

授权启用后的适配器属于受信任的传输代码。宿主应沿用现有沙箱和可用的网络／目录限制，按需注入该适配器自己的凭据，不把数据库或管理密钥交给Qwen工作会话。带平台凭据的适配器本身有发送能力；本次功能验收**不等于证明任意生成的恶意代码都无法绕过发布逻辑**。启用前按既有机制检查授权范围，不为此新建签名或安全评分平台，也不关闭已有保护。

## 5. 身份与记忆范围

本机用户、QQ 真实账号的绑定来自可信配置，不能只因昵称相同或有人说“我是他”就合并。

默认本机私聊和 QQ 私聊是不同场景。若用户明确允许同一人的私聊共享关系/回忆，配置一条明确共享范围；不是自动复制所有 transcript。首次 QQ 测试可以只确认独立场景，然后用一句获准跨私聊回忆做验证。

群聊在私聊接通后另行授权；先只开一个测试群。同群多人共享时间线、保留发言者。不能把私聊日记注入群里，也不把非白名单消息都存进全局角色上下文。

## 6. Qwen 开始开发前，Codex必须给出的可用契约

在它可读取的目录提供简短的 `RUNTIME_API.md`：实际调用方法/地址、认证来源（无秘密值）、输入与输出样例、等待输出和报告发送结果的方法、适配器允许写的目录、启动与停用命令。

**验证方式：** 一个普通本地回环事件从此入口进入，Gemma 的真实输出从此出口出来，回执可以记录。复用已有终端通道即可，不另做模型基准。

除此之外不要预先实现 NapCat 字段解析、WebSocket 客户端、QQ发送脚本或回复器。那些属于 Asuna 自己的 V2 工作。
