# ADR-014：每回合带什么、带多少——上限与她自己的笔记整理

| 项 | 内容 |
|---|---|
| 状态 | **已实施**（`context_budget.py`）。owner 2026-10-06 选定 A（上限表）与 B（她自己整理笔记），并要求顺手修 bug |
| 日期 | 2026-10-06 |
| 继承 | ADR-009（文档层、上下文块、夜间沉淀）、ADR-011（工具）、AGENTS.md（程序状态只以版本化词表进模型） |
| 作者 | 实施者（Claude），应 owner 的要求起草 |

## 一句话决定

**程序自己加进每回合的东西，由程序给上限；她自己写的、每回合都带上的笔记，由她在夜间沉淀里整理。** 什么都不悄悄截断，也不丢：没放进来的会被点数、说明，recall 仍然读得到。

## 0. owner 的要求（2026-10-06）

1. 检查喂给她的信息：是太多、不够，还是暂时合适。
2. 长期看，笔记、心得、记忆会一直长，不能有一天把提示词撑爆：要有让旧东西退下去的机制，也要有自动带入信息的上限。
3. 她的笔记整理理解为每天或每周一次的压缩：删掉旧的、过时的或已经不对的。
4. 要想清楚她长期怎么跑最好：有机制和护栏，让她有机会自己提高上下文效率，也有足够的空间去玩。

## 1. 量到的现状（2026-10-06，真实会话与库）

- 群里那一回合约 5k 字符，主要是话题线和回想。本机私聊一回合 10–20k 字符。
- 本机会话一直在 95k–200k token 之间，20 小时压缩了 8 次。DSH 按「字符数 ÷ 4」估算，她的中文实际约是这个数的 1.9 倍，所以「压缩后保留 16%」实际留下约三分之一。不会撑爆（压缩阈值用真实 token），但她每回合都在读十万以上 token，大多是旧状态。
- 三块几乎每回合重发，会话里的去重拦不住：
  - 心情原因每回合 8–39 条，最多 9k 字符，每条带 64 位 id 和「40 分钟前」这种每回合都变的时间；
  - plan 写法说明和时钟绑在一起，91 回合里重发了 86 回；
  - 记心情的词表和心情状态绑在一起。
- 无上限的：群笔记（每个群回合整份带上，公开回合也能追加）、活账、心情原因条数。过期的情感提案会永远列着（bug，目前评估路由没开，所以还没发作）。想法本按最早排、最多 20 条，暂缓的会把新想法挤出去。记忆库只增不退，但每回合只取 6 条，不影响提示词长度。

## 2. 设计

### 2.1 上限表（A）

`context_budget.py` 是一张版本化的表（`BUDGET_VERSION`）：

| 项 | 上限 |
|---|---|
| 心情原因 | 挂着的全列；其余按强弱取，总共 6 条；其余说「还有 N 笔较淡的」 |
| 群笔记每回合展示 | 2,400 字符 |
| 每份活账每回合展示 | 4,000 字符 |
| 笔记硬上限 | 展示上限的 2 倍；超过后不再接受变长的写入，变短的写入总能通过 |
| 对人的理解、character_core、current_self | 各 4,000 字符（原来 12,000） |
| 人格与口吻渲染 | 默认 16,384 字节（原来按窗口 25%，约 65k）；她能自己调到 32,768 |
| 整回合 | 48,000 JSON 字符；超过就按固定顺序去掉几个列表里最旧的行，并写 `trimmed_from_program` |

稳定的写法，让会话里的去重起作用：

- 心情原因的时间用粗档（一小时内、几小时前……），id 用 12 位前缀，`feel` 的 close 和 void 认唯一前缀；
- 钟面单独一块 `clock_from_program`，plan 写法 `schedule_control_from_program` 不再随它变；
- 记心情的词表单独一块 `how_to_record_from_program`。

### 2.2 她自己整理笔记（B）

- **展示**：没超上限就整份带上，写明「宽裕／用了一大半／快满了／超了」。超了就从新往旧放整节，放不下的只列标题，并告诉她整理一下就能都放进来。被更正过的原节和收起的节（`inject: on_demand`）不算、不带。
- **收起**：群笔记现在也能 `set_tags`，把不常用的节收起来（还在，recall 能读）。群笔记无论从哪里写都保持公开。
- **夜间整理**：夜间沉淀那一回合带 `notes_review_from_program`，列出该整理的笔记：超了、快满了，或改过之后一周没整理。每晚最多 3 份，最急的先列，附上全文。整理什么、留什么由她定，今晚不整理也可以。程序从不替她改，也不删她的字。
- **「上次整理」**：她在沉淀回合里对那份笔记的最后一次写入。

### 2.3 为什么这样分

- 上限放在程序那一侧，长期稳定，不靠她的自觉。说明一律用话，不给数字分数（AGENTS.md）。
- 退旧放在她那一侧：笔记是她的，什么过时、什么不对，只有她判断得了。程序只负责提醒、给时间、兜住最坏情况。
- 留了玩的空间：上限约是现在实际用量的 3–5 倍。不自动带上的工作文档仍只有 1 MiB 的单份上限，细节都可以放那里，笔记里留一句指路。

### 2.4 顺手修的 bug

- 过期的情感提案只在过期那一回合说一次，之后不再列出。
- 想法本先列未处理的，再列暂缓的，并说还有几条没列出。
- 未送达的出站消息正文按历史行同样截断。
- `p3_schedule_cases.py` 的离线夹具补上后来新增的同包模块，看图那条用例改成两个脑共用 read_image 之后的口径（原来就红着的 2 条）。

## 3. 没做的（owner 未选）

- C：心里话等记忆按天数退出自动回想。
- D：调低压缩后保留的比例。

以后如果记忆库的回想质量明显下降，或会话压缩仍然太频繁，再提。
